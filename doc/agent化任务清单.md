# Agent 化任务清单

本文把「分析流水线改造为 Agent」拆成可逐项实施的 T2 系列任务。T1 及其补强项（T1.1 至 T1.8）已完成，改造方案原稿见 `doc/agent化改造方案.md`，M1（计划层）已落地。

## 一、先修正一个判断

原方案把第二步定为 M2「有界重试」：证据校验失败时，由模型决定重跑哪个节点。

**这个目标偏窄。** 它只覆盖「出错后纠错」，而 Agent 的实质是「根据中间结果决定下一步做什么」。两者的区别：

| | M2 原设计 | 真正需要的能力 |
| --- | --- | --- |
| 模型看到什么 | 最终报告的证据校验结果 | **每一步执行后的中间结果** |
| 模型决定什么 | 要不要重跑、重跑哪个 | **下一步做哪个工具、还是结束** |
| 流程长度 | 仅在失败时改变 | 每次运行都不同 |
| 典型轨迹 | 固定 12 节点 + 偶发重试 | 模型自主走出 4 至 7 步 |

只做 M2，系统仍然是「固定流水线 + 一个纠错分支」。要成为 Agent，必须让模型在**执行过程中**观察并决策。本清单据此重排，原 M2 被吸收进 T2.2，不再单列。

## 二、核心约束：哪些能自主，哪些不能

不能假设「所有节点都可被模型任意重排」。当前引擎的数据流是线性强耦合的：

```text
raw → profile → quality → plan → clean → metrics → spectrum → tests
    → anomalies → changepoints → figures → report → verify
```

`clean` 是所有分析的前置产物，`plan.parameters` 决定清洗参数，所以**导入到清洗这一段必须固定顺序**。据此分三层：

| 层 | 节点 | 能否自主 | 理由 |
| --- | --- | --- | --- |
| 准备层 | 导入、规模检查、摘要、质量、场景识别、计划、清洗 | **否，固定** | 数据管道，有严格前置依赖；模型在此只能影响「计划参数」，不能改顺序 |
| 分析层 | 指标、频域、统计检验、异常、变化点、泄漏检查 | **是，模型自主** | 六者都只依赖 `(clean, plan)`，彼此无依赖，可任意顺序、可跳过、可重复 |
| 收尾层 | 图表、报告、证据校验 | **否，固定** | 聚合所有分析结果，必须最后执行 |

**Agent 化的着力点在分析层。** 这个界定让改造风险可控：数据管道与报告生成不动，25 项指标的主体口径不受影响。

## 三、目标架构

```text
固定准备：导入 → 规模 → 摘要 → 质量 → 场景 → 计划 → 清洗
                          ↓
              ┌───── Agent 循环（模型决策）─────┐
              │  观察：当前状态摘要 + 已完成工具结果  │
              │  决策：选一个工具 / 结束            │
              │  执行：调用工具，结果回灌状态        │
              └──────────────┬──────────────────┘
                          ↓
固定收尾：图表 → 报告 → 证据校验 → 落盘（含完整轨迹）
```

与现状的根本差异：现状是「先一次性规划 12 个分析项，再顺序执行」；目标是「每执行一步，模型看到结果后再决定下一步」。后者才具备真正的观察—决策—行动闭环。

## 四、任务清单

### 阶段一：打基础（T2.1 至 T2.3）

#### T2.1 分析层工具化

| 项目 | 内容 |
| --- | --- |
| 目标 | 把六个分析节点包装为统一 Tool，使其可被单独调用、跳过、重复调用 |
| 新增 | `src/mtsa/tools.py`：Tool 协议与注册表 |
| 改动 | 六个分析函数的返回结构补齐「给模型看的摘要」；引擎改为从注册表取用 |
| 关键设计 | `ToolResult` 分两路：`summary`（结构化短摘要，进模型上下文）与 `data`（完整结果，仅代码使用）。**模型永远看不到原始数组** |
| 验收 | 六个工具各自可独立调用；工具产出与现流水线逐位一致（数值一致性门槛 1e-6） |
| 风险 | 包装层引入重复计算或状态污染；须断言「同一工具重复调用结果相同」 |
| 回滚 | 工具层作为并行实现存在，引擎可切回直调函数 |

六个工具：

| 工具名 | 依赖 | 产出摘要内容 |
| --- | --- | --- |
| `compute_metrics` | clean, plan | 指标条数、关键指标（收益率、波动率、回撤等）数值 |
| `analyze_spectrum` | clean, plan | 各列主频、周期长度、谱峰显著与否 |
| `run_stat_tests` | clean, plan | 各列平稳性判定与 p 值、自相关、正态性 |
| `detect_anomalies` | clean, plan | 异常点数、按列分布、所用阈值 |
| `detect_changepoints` | clean, plan | 变化点位置与数量 |
| `check_lookahead` | clean, plan（仅股票） | 泄漏问题清单 |

#### T2.2 Agent 运行时

| 项目 | 内容 |
| --- | --- |
| 目标 | 实现观察—决策—行动循环，流程长度由模型决定 |
| 新增 | `src/mtsa/agent_runtime.py`：State、Decide、Act、Loop |
| 决策输出 | `{"action": "工具名" 或 "finish", "args": {...}, "reason": "一句话理由"}` |
| 终止条件 | 模型调 `finish`；步数达上限（默认 8）；无未执行工具且模型未结束；连续两次空转 |
| 留痕 | 每步记录：步序、动作、参数、理由、结果摘要、耗时 |
| 验收 | 同一问题多次运行，轨迹长度可以不同（证明不是固定路径）；每步理由非空 |
| 风险 | 模型可能过早结束，导致关键分析缺失；需 T2.7 的覆盖率指标兜底 |
| 回滚 | `--mode pipeline`（默认值）回到固定流水线；环境变量开关留到 T2.6 |

> **2026-10-23 实施口径**：本轮 T2.2 只接入天气场景的五个工具（指标、频域、统计检验、异常、变化点）。
> `check_lookahead` 保留在工具层供 pipeline 使用，但不进入天气白名单；股票 Agent 暂不实现，
> 请求时返回 `AGENT_SCENE_UNSUPPORTED`。

#### T2.3 观察摘要器

| 项目 | 内容 |
| --- | --- |
| 目标 | 把状态与中间结果压缩为模型可读的短摘要，控制 token 成本 |
| 新增 | `src/mtsa/observation.py` |
| 内容 | 数据概况（列名、类型、采样率、质量问题计数）；已完成工具的结果摘要；尚未执行的工具清单 |
| 策略 | 单步摘要上限约 400 token；已完成步骤保留完整摘要，更早的折叠为一行 |
| 关键约束 | **摘要只含统计量与判定结论，不含原始数据点** |
| 验收 | 7 步轨迹的上下文总量可控（目标低于 6000 token）；摘要足以支撑下一步决策 |
| 风险 | 摘要过简导致模型重复选同一工具；需在摘要中显式列出「已执行」 |

> **2026-10-23 已落地**：`src/mtsa/observation.py`；单步预算 400 token、总量 6000 token；
> 覆盖情况（工具覆盖与计划分析项覆盖）同时写入 `data.agent.coverage` 与报告。

### 阶段二：可控性（T2.4 至 T2.6）

#### T2.4 决策安全边界

| 项目 | 内容 |
| --- | --- |
| 目标 | 模型的自由限于「选哪个工具、什么顺序」，不得越界 |
| 新增 | `src/mtsa/agent_guards.py` |
| 约束 | 只能选注册表中的工具；步数上限；同一工具同参数不得重复调用（除非给出理由）；`anomaly_threshold`、`change_point_sse_ratio`、`close_column` 等标定参数不可修改（沿用 M1 锁定清单） |
| 越界行为 | 拒绝该动作，把拒绝原因回灌模型，让它重选；连续越界则终止并标注 |
| 验收 | 构造越界动作（未知工具、改锁定参数、重复调用），均被拦截且留下事件 |
| 风险 | 拦截过严会让模型陷入重试；须限制连续拒绝次数 |

> **2026-10-23 已落地**：`src/mtsa/agent_guards.py`；越界按类型留痕，
> 连续 3 次终止；失败工具允许重试一次。

#### T2.5 轨迹持久化与重放

| 项目 | 内容 |
| --- | --- |
| 目标 | 可复现性从「代码确定」转为「轨迹可重放」 |
| 新增 | `result.json` 增加 `data.agent_trajectory`；CLI 增加 `--replay` |
| 轨迹内容 | 每步的动作、参数、理由、结果摘要、耗时、模型标识；末尾附轨迹哈希 |
| 重放 | 读取轨迹，按原顺序重跑工具，不走模型；断言结果与原运行逐位一致 |
| 验收 | 同一轨迹重放，`result.json` 除 `run_id` 与时间戳外逐字节一致 |
| 意义 | 这是 Agent 模式下「可复现」的唯一可靠保障——不能指望模型两次输出相同路径 |

> **2026-10-23 已落地**：`src/mtsa/replay.py` + CLI `--replay`；轨迹哈希与数据双重比对，
> 不一致返回 `REPLAY_MISMATCH`。
| 风险 | 工具内部若有随机性（如随机种子未固定），重放会失败；须先审计各工具的随机源 |

#### T2.6 双模式并存

| 项目 | 内容 |
| --- | --- |
| 目标 | 保留确定性流水线作为对照与兜底，不因改造丢掉已验证能力 |
| 新增 | CLI `--mode pipeline \| agent \| auto`；`auto` 为无模型配置时回落 pipeline |
| 行为 | `pipeline` 走现有 12 节点顺序，行为与 T1.8 完全一致；`agent` 走自主循环 |
| 验收 | `pipeline` 模式下 25 项指标数值与 T1.8 逐位一致 |
| 意义 | 让「Agent 是否更好」成为一个可测量的对照实验，而不是主观判断 |

> **2026-10-23 已落地**：`--mode pipeline|agent|auto` + `MTSA_AGENT`；
> auto 在非天气或无模型时回退 pipeline；pipeline 指纹与基线一致。

#### T2.7 失败恢复

| 项目 | 内容 |
| --- | --- |
| 目标 | 单个工具失败不应让整次运行崩溃 |
| 行为 | 工具抛异常时，把错误摘要回灌模型；模型可换工具、改参数或跳过并把该分析标注为「未完成」 |
| 硬失败 | 准备层（导入、摘要、清洗）失败仍直接中止——这些无法降级 |
| 验收 | 注入工具异常，运行仍能完成，且报告中明确标注哪项分析失败及原因 |
| 风险 | 「跳过」可能掩盖真实问题；需在结论与报告中显式标注，不得静默 |

> **2026-10-23 已落地**：`tool_states` 区分 ok/skipped/failed/not_run；
> 报告新增「失败工具」「跳过工具」，warnings 措辞区分。

### 阶段三：验证（T2.8 至 T2.9）

#### T2.8 评估指标扩展

| 项目 | 内容 |
| --- | --- |
| 目标 | 度量 Agent 行为本身，而不只是最终数值 |
| 新增指标 | 平均步数、终止原因分布、关键分析覆盖率、轨迹可重放率、越界拒绝次数 |
| 关键指标解释 | **关键分析覆盖率**：对照规则计划的 12 项分析，Agent 轨迹是否遗漏了与问题直接相关的项。这是防「模型过早结束」的核心指标 |
| 不改动 | 原有 25 项指标在 `pipeline` 模式下的口径与阈值完全不变 |
| 验收 | 新增不少于 4 项指标，且每项都有专项测试 |
| 风险 | 「路径合理性」难以客观判定；建议先只度量可机械判定的覆盖度，不引入人工评分 |

> **2026-10-23 已落地**：新增 `evals/agent_eval.py`（9 个天气用例）与
> `tests/test_agent_eval.py`（11 项）。指标含平均步数、终止原因分布、工具覆盖率、
> 计划分析项覆盖率、**对照规则计划 12 项的需求覆盖率**、轨迹可重放率、越界拒绝、
> 工具失败率、耗时与 token（服务端返回 `usage` 时）。
> 口径要点：验收看需求覆盖率；规则计划覆盖率只做广度对照。重放比对已修正

#### T2.9 对照实验与结论

| 项目 | 内容 |
| --- | --- |
| 目标 | 给出「Agent 相对固定流水线好在哪、差在哪」的实测答案 |
| 方法 | 同一批问题（复用 `evals/llm_eval.py` 的 9 个用例），两种模式各跑一遍 |
| 对比维度 | 关键分析覆盖率、结论条数、耗时、token 成本、轨迹长度分布、可重放率 |
| 产出 | 对比表写入评估记录与改进记录，含失败样例分析 |
| 验收 | 结论部分必须同时写出 Agent 的**劣势**（如成本更高、路径不稳定），不得只报优点 |
| 风险 | 样本量小导致结论不稳；至少各跑 9 个用例，并在文档中标注样本量 |

> 报告变窄、端到端更慢、路径不稳定。详见 `evals/评估记录.md` 第 12 轮。

## 五、依赖与建议顺序

```text
T2.1 工具化
  └→ T2.2 运行时
       ├→ T2.3 观察器
       ├→ T2.4 安全边界
       └→ T2.7 失败恢复
            └→ T2.5 轨迹重放
                 └→ T2.6 双模式
                      └→ T2.8 指标扩展
                           └→ T2.9 对照实验
                                └→ T2.10 文档收口
                                     └→ T2.11 输出稳定性
```

T2.3 与 T2.4 可并行；T2.5 必须在其后，因为轨迹格式要包含观察与拦截结果。

**建议从 T2.1 开始。** 它是唯一「不改行为、只改结构」的任务，可以先把工具层建起来并用现有测试证明「逐位一致」，再往上叠循环。这样即使后续循环设计需要反复调整，底层工具层是稳定的。

## 六、口径变化（必须提前说明）

Agent 模式下有几项现有指标的含义会改变，不能沿用旧口径宣称达标：

| 指标 | 流水线模式 | Agent 模式 |
| --- | --- | --- |
| 重复运行一致率 | 同代码同输入，结果确定一致 | **不再由代码保证**；改由「轨迹可重放率」保障 |
| 方法选择准确率 | 由规则计划决定，恒为 1.00 | 由模型轨迹决定，可能低于 1.00，须如实报告 |
| 异常检测 P/R | 分析必跑 | 若模型未选异常分析，该指标**无值**，不能记 0 或 1 |
| 无证据结论数 | 结论由适配器生成 | 仍为 0，但须新增「未完成分析是否被标注」的检查 |

因此评估体系必须按模式分栏，不允许把两种模式的数字混在一张表里比较。

## 七、不做的事

| 事项 | 理由 |
| --- | --- |
| 让模型决定数据管道顺序 | `clean` 是全部分析的前置，乱序无意义，只会制造失败 |
| 让模型参与数值计算 | 违反项目底线；数值必须由代码产出且可复算 |
| 多 Agent 协作（规划、执行、评估分角色） | 单 Agent 闭环尚未验证前引入多角色，只会把问题复杂化；且无法说明各自的贡献 |
| 无限步数自主 | 成本不可控，且步数越多越容易陷入空转；上限 8 步已覆盖 6 个工具 |
| 用第二个模型给第一个模型打分 | 裁判本身需要验证，等于把问题推后一层；改用可机械判定的覆盖度指标 |
| 放弃固定流水线 | 它是唯一已验证通过的路径，也是对照基线 |

## 八、总体验收标准

改造全部完成后，需同时满足：

1. `pipeline` 模式下 25 项指标数值与 T1.8 逐位一致（证明没有破坏已验证能力）。
2. `agent` 模式下轨迹长度可变，且每步都有非空理由（证明流程由模型决定）。
3. 任一轨迹可重放，重放结果逐字节一致（证明可复现性未失守）。
4. 关键分析覆盖率不低于 0.80（证明模型没有为了省事而过早结束）。
