# 第三阶段报告：Agent 化改造（仅天气）

> 日期：2026-10-23
> 范围：`multi_source_timeseries_analysis` 的 Agent 化任务 T2.2–T2.10
> 边界：**Agent 只实现天气场景**；股票 Agent 未实现，请求会返回 `AGENT_SCENE_UNSUPPORTED`

## 1. 这一阶段做了什么

把分析层从「固定流水线」改造成「模型在白名单内选择工具」的循环，并补齐可控性与验证：

| 能力 | 实现 | 证据 |
| --- | --- | --- |
| 观察—决策—行动循环 | `agent_runtime.py` | `tests/test_agent_runtime.py` |
| 观察摘要（预算 400/6000 token） | `observation.py` | `tests/test_observation.py` |
| 决策边界与失败恢复 | `agent_guards.py` | `tests/test_agent_guards.py` |
| 轨迹哈希与离线重放 | `replay.py`、`--replay` | `tests/test_replay.py`、真实重放 |
| 三模式并存 | `--mode pipeline\|agent\|auto`、`MTSA_AGENT` | `tests/test_modes.py` |
| Agent 评估指标 | `evals/agent_eval.py` | `evals/agent_eval_results.json` |
| 两模式对照 | `evals/mode_compare.py` | `evals/mode_compare_results.json` |

## 2. 怎么运行

```powershell
# 1) 模型配置（用户级，新终端生效）
[Environment]::SetEnvironmentVariable('MTSA_LLM_BASE_URL','https://api.deepseek.com/v1','User')
[Environment]::SetEnvironmentVariable('MTSA_LLM_MODEL','deepseek-chat','User')
# MTSA_LLM_API_KEY 需自行配置，不要写进仓库

# 2) Agent 运行（仅天气）
python -m mtsa.cli run --mode agent --scene weather `
    --input fixtures/weather_v1.csv --question "分析温度的趋势、季节性与极端事件"

# 3) 离线重放（不调用模型）
python -m mtsa.cli run --replay artifacts/<run_id>/result.json

# 4) 自动模式（无模型/非天气回退 pipeline）
python -m mtsa.cli run --mode auto --scene weather --input fixtures/weather_v1.csv --question "..."

# 5) 评估
python -m evals.agent_eval          # 9 用例；真实模型
python -m evals.agent_eval --mock   # 只验证指标管线
python -m evals.mode_compare        # pipeline / agent 对照
```

评估与回归测试必须固定规则计划，避免计划层差异混入：

```powershell
$env:MTSA_PLANNER = "rule"
```

## 3. 验证结果

### 3.1 测试

`tests/` 共 **270 项 / 28 个文件**，逐个文件运行全部退出码 0。
单进程跑全量在本机会环境级卡死（CPU 归零、无报错），因此按文件隔离验证；
日志在 `evals/test_logs/`（每个文件一份）。

### 3.2 真实模型（DeepSeek `deepseek-chat`，9 个天气用例）

```text
9/9 成功，平均 3.33 步，全部 model_finished
需求覆盖率 1.00；工具覆盖率 0.667；规则计划覆盖率 0.657
可重放率 1.00（9/9）；越界 1 次（duplicate_tool）；工具失败率 0.00
平均耗时 10.99 s；token 45,021（平均 5,002/次）
```

### 3.3 两模式对照（同一份 12 项规则计划）

| 维度 | pipeline | agent | 差值 |
| --- | --- | --- | --- |
| 成功 | 9/9 | 9/9 | 0 |
| 分析单元 / 步数（均值） | 5.00 | 3.67 | −1.33 |
| 结论（均值） | 39.00 | 26.78 | −31.3% |
| 需求覆盖率 | 1.00 | 1.00 | 0 |
| 规则计划覆盖率 | 1.00 | 0.72 | −0.28 |
| 墙钟（均值） | 50.5 s | 52.9 s | +4.7% |
| token | 0 | 48,565 | — |

### 3.4 回归

- 天气 pipeline 的分析指纹与阶段 0 基线一致；
- `mode=agent` 请求股票场景返回 `AGENT_SCENE_UNSUPPORTED`，不静默降级；
- 无模型时 `agent` 返回 `AGENT_UNAVAILABLE`，`auto` 回退 pipeline 并写 warning。

## 4. 结论

**Agent 的优势**

1. 需求覆盖不降：8 个有明确需求的用例全部 1.00。
2. 窄问题更省：`wx_normal` 只需 1 步、1 条结论、2,090 token；pipeline 固定 39 条。
3. 路径可审计、可重放：轨迹落盘，9/9 重放一致。

**Agent 的劣势**

1. 报告信息量下降 31%，窄问题可能只有 1 条结论。
2. 端到端没有更快（+4.7%）：图表/报告是固定成本，模型调用又加延迟。
3. 广度下降：规则计划覆盖 1.00 → 0.72。
4. 输出不稳定：同一问题跨运行步数会变（3 ↔ 5）。
5. 有 token 成本（约 5.4k/次）。

**选型建议**：要完整报告用 pipeline；问题窄、在意成本、需要审计路径用 agent；
默认保持 pipeline，Agent 需显式开启。

## 5. 已知限制

- 仅天气场景；股票 Agent 未实现；
- 9 个用例、单模型、单计划层，不构成统计显著性证据；
- 覆盖率只衡量「分析是否执行」，不衡量检出正确性；
- 墙钟含约 40 s 量级的图表渲染，绝对值随机器变化；
- 没有 token 预算与最少覆盖硬约束；
- 单进程全量测试在本机会环境级卡死，改用 7 组分别运行验证。
