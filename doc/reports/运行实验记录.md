# 多源时序分析 Agent 运行实验记录

## 一、实验目的与范围

### 1.1 目的

本记录承接 Agent 化改造第一步（M1 计划层）的完成，目的有三：

其一，验证模型是否真正参与分析决策。改造前，十二个节点的执行路径全部由代码固定，模型不介入；改造后，节点「场景识别与计划」改由模型从工具集中选择分析项，规则作为兜底。这一改变是否生效，不能靠读代码断言，必须由运行时证据证明。

其二，记录每次运行的完整流程，使结果可复现、可追溯。包括环境准备、命令、产物、观测到的异常与处理方式。

其三，暴露改造引入的新风险。模型参与决策必然带来覆盖面变化与不确定性，这些必须如实记录，而不是只报告「跑通了」。

### 1.2 范围

记录对象为 M1 完成后的全部真实运行，共五组实验，编号 R1 至 R5。不包含单元测试与批量评估（另有记录），也不包含改造前的历史运行。

### 1.3 判定标准

一次运行视为「模型计划生效」，需同时满足三条：

| 编号 | 判据 | 说明 |
| --- | --- | --- |
| C1 | `plan_source` 为 `llm` | `cache` 表示命中缓存未调用模型，`rule` 表示回退 |
| C2 | 运行无中断且产物完整 | 报告、结构化结果、图表均生成 |
| C3 | `warnings` 中无计划层回退记录 | 有回退说明模型输出未通过校验 |

三条缺一不可。仅看运行是否成功不足以判定，因为回退到规则计划时运行同样成功。

## 三、运行流程

### 3.1 环境变量准备

`mtsa` 包未安装到虚拟环境的 site-packages，运行时需显式指定导入路径：

```powershell
cd <repo>
$py = "<venv>\Scripts\python.exe"
$env:PYTHONPATH = "$PWD\src"

$env:MTSA_LLM_BASE_URL = "https://api.deepseek.com/v1"
$env:MTSA_LLM_MODEL    = "deepseek-chat"
$env:MTSA_LLM_API_KEY  = [Environment]::GetEnvironmentVariable('MTSA_LLM_API_KEY','User')
```

最后一行从用户级变量重新读取，而非直接赋值。原因是当前会话中的变量可能已被覆盖成字面量，从注册表读回可避开这一状态。

### 3.2 缓存机制与「真实调用」的判定

计划层带缓存，键为 `sha1(版本 | 场景 | 问题 | 列名 | 行数)`，落盘于 `artifacts/plan_cache/`。命中时 `plan_source` 为 `cache`，不再请求模型。

这意味着：相同问题与相同数据第二次运行不会消耗 token，但也**不会产生新的模型输出**。若目的是验证模型能力，必须先清空缓存：

```powershell
Remove-Item artifacts\plan_cache\*.json -Force
```

本记录中 R2 与 R5 为真实调用，R3 为刻意的缓存命中验证。

### 3.3 执行命令与产物结构

```powershell
& $py -m mtsa.cli run --scene weather --input fixtures\weather_v1.csv `
    --question "分析温度的趋势、季节性与极端事件" --output artifacts\final_run
```

产物共 18 个文件，结构如下：

| 类别 | 文件 | 说明 |
| --- | --- | --- |
| 报告 | `report.md` | 人读报告，含数据概况、指标表、结论与证据 |
| 结构化结果 | `result.json` | 完整结果，含计划、指标、异常、变化点、证据、告警 |
| 复现脚本 | `reproduce.py` | 记录本次运行参数，可原样重跑 |
| 清洗后数据 | `clean_data.csv` | 清洗与单位换算后的数据 |
| 交互图 | `fig_01` 至 `fig_07` 的 `.html` | 可缩放、可悬停 |
| 静态图 | `fig_01` 至 `fig_07` 的 `.png` | 报告用，依赖浏览器渲染 |

### 3.4 计划层校验与兜底链

模型输出不直接执行，需经三级校验：

| 层级 | 检查内容 | 失败处理 |
| --- | --- | --- |
| 格式 | 是否为合法 JSON 对象 | 重试一次，仍失败则回退 |
| schema | 字段类型、必填项 | 回退规则计划 |
| 语义 | 工具名是否在白名单、列是否存在、参数是否合法、是否触碰锁定参数 | 回退规则计划 |

兜底顺序为：缓存 → 模型 → 规则。锁定参数包括 `anomaly_threshold`、`change_point_sse_ratio`、`close_column`，这三项是统计标定结果与场景结构参数，不允许模型改动。

## 四、实验记录

### 4.1 R1 规则模式基线

**目的。** 建立参照系：不使用模型时的行为与耗时。

**配置。** `MTSA_PLANNER=rule`，或清空全部 `MTSA_LLM_*` 变量。

**观测。**

| 项目 | 结果 |
| --- | --- |
| 耗时 | 37 秒 |
| `plan_source` | `rule` |
| 分析项数量 | 12 项（趋势、相关、滞后、极值、频谱、变化点、异常、四类检验等） |
| `warnings` | 0 |

**结论。** 规则计划覆盖面广，十二项分析全跑，适合需要完整体检的场景。耗时 37 秒，其中统计检验占比最大——这与性能基准中「统计检验占 1e5 行时总耗时 90%」的判断一致。

### 4.2 R2 LLM 模式首次运行

**目的。** 验证模型计划能否生效。

**前置。** 清空缓存，确保真实调用。

**观测。**

| 项目 | 结果 |
| --- | --- |
| 耗时 | 25 秒 |
| `plan_source` | `llm` |
| 模型选中分析项 | `trend`、`seasonal`、`extreme`（3 项） |
| `warnings` | 0 |

**判定。** C1、C2、C3 均满足，模型计划生效。

**发现。** 模型只选了 3 项，远少于规则计划的 12 项。这不是缺陷，而是「由模型决定范围」的直接后果：它判断该问题只需三类分析。但同时带来一个重要副作用——未选中的分析项不会执行，其对应结果为空。

### 4.3 R3 缓存命中验证

**目的。** 确认缓存键有效，且重复运行不重复消耗 token。

**观测。**

| 项目 | 结果 |
| --- | --- |
| 耗时 | 22.3 秒 |
| `plan_source` | `cache` |
| 分析项 | 与 R2 完全一致 |
| 模型调用 | 未发生 |

**结论。** 缓存有效。同一问题与同一数据的重复运行成本恒定，且结果一致——这为「可复现」提供了基础。

**风险提示。** 缓存也是误判来源。用户若在缓存存在时运行，看到 `plan_source=cache` 会以为模型也未参与，实际是此前参与过。判定「模型是否生效」必须结合是否清空缓存。

### 4.4 R4 静态图导出故障与对照实验

**现象。** 用户本地终端两次运行，7 张 PNG 全部失败，HTML 全部成功。错误为 `BrowserFailedError: The browser seemed to close immediately after starting`，尝试启动的浏览器为 `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`。

**对照实验。** 同一台机器、同一份代码、同一时段，由代理执行三次，全部成功：

| 次数 | 时刻 | 环境条件 | 结果 |
| --- | --- | --- | --- |
| 1 | 23:21 | 常规 | 成功，7 张 PNG |
| 2 | 23:36 | 独立输出目录 | 成功，7 张 |
| 3 | 23:49 | 浏览器已有 8 个进程在运行 | 成功，7 张 |

**排除的假设。** 最初推测「Edge 已在运行导致新实例立即退出」，被第 3 次实验推翻——浏览器进程占用时导出依然成功。

**未定位的部分。** 差异确定在进程环境，但未能缩小到具体变量。用户终端与工作环境的环境变量、会话标识、权限均未逐项比对完毕。

**已做的加固。** 原实现单次尝试即放弃，且失败时不清理同名旧图。现改为：

| 改动 | 作用 |
| --- | --- |
| 失败后等待重试一次 | 覆盖瞬时故障 |
| 最终失败删除同名旧 PNG | 防止上一次的图冒充本次结果 |
| 告警附可操作修复建议，仅首次给出 | 避免同一建议重复七条 |
| 建议中剔除下载 Chrome 的方案 | 该源在本机实测超时不可达 |

**必须记录的隐患。** 故障时目录中仍存在 7 张 PNG，时间戳为上一次运行。若不核对时间戳，会误判为「本次生成成功」。这一掩盖比缺文件更危险，也是本轮加固中最重要的一条。

### 4.6 实验汇总

| 编号 | 模式 | 耗时 | `plan_source` | 分析项 | 静态图 | 告警 |
| --- | --- | --- | --- | --- | --- | --- |
| R1 | 规则 | 37 秒 | `rule` | 12 | 7 张 | 0 |

## 五、结果与结论

### 5.1 数据概况

| 项目 | 取值 |
| --- | --- |
| 输入文件 SHA1 | `586044dacea419b41dd70b56122abc7ccb2fd4de` |
| 原始行数 | 34793 |
| 清洗后行数 | 17530 |
| 时间范围 | 2024-01-01 至 2025-12-31，小时级 |
| 站点数 | 2（STA_A、STA_B） |

### 5.2 分析结论

以下六条为 R5 的实际输出，均绑定证据编号。

| 编号 | 结论 |
| --- | --- |
| E1 | `temperature@STA_A` 在 2024-05-05 至 2024-06-04 区间被识别为华氏度段，共 713 个采样点，已统一换算为摄氏度，区间中位数 76.94 换算为 24.97 |
| E2 | `temperature@STA_A`：Mann-Kendall τ=0.0544，p=3.332e-27，存在显著单调趋势，方向上升；月度均值 OLS 斜率 +0.1267 单位/月 |
| E3 | `temperature@STA_A`：月均振幅 23.567，峰值月 7 月，谷值月 1 月 |
| E4 | `temperature@STA_B`：Mann-Kendall τ=-0.0709，p=5.342e-45，存在显著单调趋势，方向下降；月度均值 OLS 斜率 -0.1409 单位/月 |
| E5 | `temperature@STA_B`：月均振幅 22.623，峰值月 6 月，谷值月 12 月 |
| E6 | `temperature@STA_A` 与 `temperature@STA_B`：Pearson 相关系数 0.792，正相关，强度为强 |

### 5.3 对结论的解读

两个站点呈现出**方向相反的趋势**：STA_A 上升、STA_B 下降，两者的 p 值分别为 3.3e-27 与 5.3e-45，远超常规显著性门槛，不可能是随机波动。同时两者相关系数 0.792，说明日常波动高度同步。

这组事实指向一个明确判断：**两个站点的季节循环几乎一致，但长期基线正在分离**。若这是真实观测数据，应优先排查两个传感器是否存在系统性漂移或校准差异；若为合成数据，则说明生成器刻意注入了反向趋势。

需要注意，趋势是统计意义上的单调性，不等于因果。斜率数值较小（每月 0.13 与 0.14 个单位），外推时须谨慎。

### 5.4 计划层行为观察

| 观察项 | 结果 | 评价 |
| --- | --- | --- |
| 是否真实调用模型 | 是（R2、R5） | `plan_source` 为 `llm` |
| 模型是否按问题选择分析 | 是 | 问题问趋势、季节性、极端事件，选中三项对应分析 |
| 是否触碰锁定参数 | 否 | 阈值与判据未被修改 |
| 缓存是否生效 | 是 | 二次运行不再调用 |
| 回退是否发生 | 否 | 三次真实运行均无回退告警 |

### 5.5 一处必须澄清的误读风险

R5 中异常与变化点结果**为空**。原因不是「检测后未发现异常」，而是**模型没有选择这两项分析**，对应计算根本没有执行。

两者含义完全不同：

| 表述 | 含义 |
| --- | --- |
| 未跑异常检测 | 系统不知道有没有异常 |
| 跑了但未检出 | 系统判断没有异常 |

若把前者误读为后者，会得出「该数据无异常」的错误结论。本记录在摘要、第五章与第八章均标注了这一点，后续交付中亦须保留该说明。

## 六、问题记录与处理

### 6.1 工具名与下游消费点不一致

**现象。** 模型选择的工具名能通过白名单校验，写入计划的分析项列表，但对应分析一项都不执行。

**根因。** 工具集按分析大类命名（如 `correlation`、`stat_tests`），而引擎实际判断的是细粒度名（如 `corr`、`test`、`stationarity`）。名字对不上不会报错，只会安静地什么都不做。

**处理。** 工具集改为下游真实的 13 个名字；新增一致性测试，断言工具名集合必须等于下游消费点集合。

**教训。** 凡是「模型输出、下游消费」的接口，名字不匹配不会报错，只会静默失效。此类失效必须用断言锁死，人工核对不可靠。

### 6.2 配置不全时静默回退

**现象。** 配了密钥但漏了 `BASE_URL`，运行成功，`plan_source` 为 `rule`，无任何提示。

**根因。** 构建计划器时，任一配置缺失即返回规则计划器，且不留痕迹。

**处理。** 区分三种情形：

| 情形 | 行为 |
| --- | --- |
| 两项都未配 | 静默走规则（默认用法） |
| 配了一半 | 回退，并把缺失变量名写入告警 |
| 显式要求模型却未配 | 回退，并点名两项均缺 |

**理由。** 「一个都没配」是用户本就要用规则模式，提示属噪音；「配了一半」是配置错误，必须暴露。二者不能一视同仁。

### 6.3 静态图导出失败

见 4.4。已加重试、残留清理与可操作提示，新增五项测试。根本的环境差异未定位。

### 6.4 命令行路径反斜杠被转义

**现象。** 读取结果文件时报 `OSError: [Errno 22] Invalid argument`。

**根因。** Python 字符串中 `\r` 是回车符，路径 `artifacts\run_llm\result.json` 被解析为 `artifacts` 加回车加 `un_llm\result.json`。

**处理。** 路径统一使用正斜杠，或使用原始字符串前缀。这条已写入使用约定，不涉及代码修改。

## 七、已知限制与不适用场景

1. **模型模式覆盖面窄于规则模式。** 本次为 3 项对 12 项。需要完整分析时应改用规则模式，或在问题中明确要求。
2. **模型输出非严格确定。** 温度固定为 0 且带缓存，但缓存未命中时两次调用仍可能给出不同计划。计划一致率应如实观测，不设门槛。
3. **静态图导出依赖外部浏览器。** 该依赖在特定进程环境下稳定失败，原因未定位。交互图不受影响。
4. **异常与变化点判据仍是统计标定结果。** 异常阈值在开发集选定，变化点可靠检出下限约为噪声标准差的 7.9 倍，两者均不可跨数据集直接套用。
5. **单一场景验证。** 本次运行只覆盖天气场景；股票场景的模型计划未做同级别验证。
6. **未做长时稳定性验证。** 以上实验均为单次运行，未覆盖连续多次运行的内存与句柄累积情况。

| 实验编号与时刻 | 便于对照 |
| 是否清空缓存 | 决定 `plan_source` 的可能取值 |
| 模式与配置 | 规则 / 模型，模型名 |
| 耗时 | 与实际规模对应 |
| `plan_source` | 判定模型是否生效的核心依据 |
| 分析项与目标列 | 决定结果覆盖范围 |
| 静态图与交互图数量 | 判断产物完整性 |
| 告警条数 | 非零时必须逐条说明 |
| 结论与证据数 | 应一一对应，数量不等即存在问题 |

### 8.3 交付方式

后续运行由代理执行，交付三部分：产物路径、结论摘要、关键图。交付时必须同时说明本次未执行哪些分析，避免空结果被误读为阴性结论。

### 8.4 判定清单

每次运行后按下表逐项确认，全部通过方可视为一次有效实验。

| 检查项 | 通过条件 |
| --- | --- |
| 模型是否生效 | `plan_source` 为 `llm` |
| 产物是否完整 | 静态图与交互图数量一致且等于图表规格数 |
| 告警是否可解释 | 每条告警均有明确原因与处理方式 |
| 结论是否有据 | 结论数与证据数相等 |
| 覆盖范围是否注明 | 已说明未执行的分析项 |
