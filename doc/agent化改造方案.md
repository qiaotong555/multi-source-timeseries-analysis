## 一、现状判定

### 1.1 当前是什么

当前系统是一条**确定性流水线**：十二个节点按固定顺序执行，节点的进入与退出条件由代码判断，场景与分析项的确定由适配器规则完成，全链路没有任何 LLM 调用。

它不是一般意义上的 workflow。按照业界通行的划分，workflow 至少还有 LLM 参与编排（prompt chaining、routing、orchestrator-workers 都由 LLM 做分流）。本系统的分流完全由规则完成，因此更准确的定位是 pipeline。

### 1.2 与 Agent 定义的差距

课程规范把后缀 Agent 定义为「模型根据状态动态选择工具或步骤」。逐条对照如下。

**表 1-1 四项差距**

| 维度 | Agent 的要求 | 当前实现 | 差距 |
| --- | --- | --- | --- |
| 流程决定权 | 模型根据状态选择步骤 | 十二节点顺序由代码固定 | 无决策权 |
| 工具选择权 | 模型运行时从工具集挑选 | 分析项由适配器规则确定 | 无选择权 |
| 模型参与度 | 模型在回路内 | 全链路无模型调用 | 未接入 |
| 终止条件 | 模型判断完成 | 走完第十二节点即结束 | 固定长度 |

四项全部不满足，因此按定义不构成 Agent。

### 1.3 当初为什么这样设计

第一阶段的报告已记录这一取舍：规范 1.3 节要求模型动态选择步骤，规范 2.3 节又要求确定性规则由代码执行，两条叠加后若让模型自由决定分析路径，同一份数据两次运行会得到不同结果，与「可复现」直接冲突。

这个推理成立，它解决了确定性与可复现的矛盾，但没有解决形态归属问题。本方案要做的是：**在保住可复现的前提下，把决策权交还给模型。**

## 二、改造目标

### 2.1 目标形态

受控 Agent：模型负责「用什么工具、分析什么、怎么分步」，代码负责「怎么算、算得对不对」。

关键区别于自由 Agent 的地方有三点：

1. 模型的输出是**结构化计划**，不是自然语言指令，必须通过 schema 校验才能执行
2. 模型**不能产出任何数值**，所有指标仍由确定性代码计算
3. 模型的决策范围有**白名单边界**，超出边界的字段直接拒绝

### 2.2 三条不可让渡的底线

| 底线 | 含义 | 保障手段 |
| --- | --- | --- |
| 可复现 | 同一计划下执行结果完全一致 | 计划缓存 + 温度 0 + 数值不经过模型 |
| 证据可追溯 | 每条结论绑定指标、产物与代码位置 | 现有证据链机制不变，计划本身也写入结果 |
| 契约结构化 | 输入输出经 Pydantic 校验 | 计划在进入执行前完成三级校验 |

任何改造若破坏这三条，视为方案失败，不接受。

### 2.3 目标架构

```
            自然语言问题 + 数据摘要
                     │
                     ▼
        ┌────────────────────────┐
        │   Planner（可插拔）      │
        │  ┌──────────────────┐  │
        │  │ LLMPlanner       │  │  模型决定：选哪些工具、分析哪些列、什么窗口
        │  │  ↓ 校验失败/超时  │  │
        │  │ RulePlanner      │  │  规则兜底：适配器现有逻辑
        │  └──────────────────┘  │
        └───────────┬────────────┘
                    ▼
           AnalysisPlan（经三级校验）
                    │
                    ▼
        节点 05 至 12（完全不变，确定性执行）
                    │
                    ▼
        result.json（含 plan 与 plan_source）
```

变化只发生在节点 04。节点 01 至 03 是数据准备，节点 05 至 12 是计算与交付，均不感知计划来自模型还是规则。

## 四、详细设计

### 4.1 Planner 协议

统一入口，返回计划与来源，调用方据此记录留痕。

```
class Planner(Protocol):
    def plan(self, question: str, profile, qrep, adapter, frame) -> tuple[AnalysisPlan, str]
```

返回的第二个元素是 `plan_source`，取值 `llm`、`rule`、`mock`、`cache`。该值写入 result.json 与事件轨迹，用于事后审计。

### 4.2 工具集定义

模型可选的分析项就是「工具」，共八项，与现有分析能力一一对应。

**表 4-1 八个可选工具**

| 工具名 | 能力 | 适用条件（供模型判断） |
| --- | --- | --- |
| `trend` | 趋势与斜率 | 存在单调性或长周期 |
| `volatility` | 波动率与滚动标准差 | 关注稳定性 |
| `correlation` | 列间相关与滞后相关 | 多列且存在物理关联 |
| `spectrum` | Welch 功率谱与主频 | 采样均匀、样本量足够 |
| `stat_tests` | 平稳性、自相关、正态性等六类 | 需要推断性结论 |
| `anomaly` | 异常点检测 | 关注离群与故障 |
| `changepoint` | 均值与方差突变 | 关注结构变化 |
| `scenario_metrics` | 场景专属指标 | 场景适配器已实现 |

工具描述文本会随请求一并发给模型，让模型基于「数据特征 + 问题意图」选择，而不是靠猜名字。

### 4.3 请求构造

输入只传摘要，不传原始数据。这是成本控制，也是防止模型越界。

**表 4-2 请求内容**

| 字段 | 内容 | 说明 |
| --- | --- | --- |
| `question` | 用户的自然语言问题 | 原文 |
| `scene_candidates` | 场景候选与置信度 | 来自节点 04 的 detect 结果 |
| `columns` | 列名、类型、缺失率、取值范围 | 摘要，非原始值 |
| `sampling` | 中位间隔、样本量、是否存在缺口 | 决定频域与检验是否可行 |
| `quality` | 各类质量问题的计数 | 让模型知道数据有多脏 |
| `tools` | 八个工具的名字与描述 | 工具集 |
| `constraints` | 不得修改的参数字段清单 | 硬边界 |

单次请求不含任何时间序列数值，输入规模与数据行数无关，只与列数相关。这是把 LLM 引入流水线后成本可控的关键。

### 4.4 三级校验

模型输出必须依次通过三道校验，任何一道失败即进入兜底链。

**表 4-3 校验链**

| 层级 | 校验内容 | 失败处理 |
| --- | --- | --- |
| 一级：格式 | JSON 可解析，字段类型正确 | 重试一次，仍失败则回退 |
| 二级：schema | 符合 plan.json 定义，必填项齐全 | 重试一次，仍失败则回退 |
| 三级：语义 | 工具名在白名单内；目标列存在于实际数据；参数在允许范围内 | 直接回退，不重试 |

三级校验中，语义校验最关键。它拦住的典型错误是：模型编造不存在的分析项、指定数据集里没有的列、把窗口设成负数。

### 4.5 兜底链

四级递进，任何一级成功即停止。

**表 4-4 兜底顺序**

| 顺序 | 来源 | 触发条件 | plan_source |
| --- | --- | --- | --- |
| 1 | 计划缓存 | 问题与数据摘要的哈希命中 | `cache` |
| 2 | LLMPlanner | 配置了端点与密钥 | `llm` |
| 3 | RulePlanner | 未配置、超时、校验失败 | `rule` |
| 4 | 最小可用计划 | 规则也失败（极罕见） | `rule`，并记告警 |

第四级是最后防线：仅包含 `trend` 与 `anomaly` 两项，保证流水线不因计划层问题而整体失败。

### 4.6 计划缓存

缓存键为 `sha1(question 规范化 + 数据摘要哈希 + planner_version)`，值为计划 JSON。

命中缓存时不再调用模型，`plan_source` 记为 `cache`。这一机制同时解决三个问题：重复运行的一致性、调用成本、以及模型服务不可用时的可用性。

缓存不做自动失效，`planner_version` 变更时整体失效。这是有意的：宁可手动清缓存，也不接受「悄悄用了旧计划」这种隐式行为。

### 4.7 决策留痕

计划与来源写入 result.json 的 `data.plan`，并新增两个字段：

| 字段 | 内容 |
| --- | --- |
| `plan_source` | `llm` / `rule` / `cache` / `mock` |
| `planner_version` | 提示词与校验规则的版本号，变更时递增 |

事件轨迹中新增一条 `plan` 事件，记录来源、耗时、是否回退、回退原因。评估时可直接统计回退率。

### 4.8 有界重试（第二阶段内容）

第一阶段的改造到计划层为止。若要进一步接近真正的 Agent，需要引入「评估—重试」循环：

```
执行完节点 12 → 证据校验
                  ├─ 通过 → 结束
                  └─ 失败 → 模型判断：重跑哪个节点、改什么参数
                              ├─ 有判断 且 未超上限 → 回到该节点
                              └─ 无判断 或 已达上限 → 结束并标注未达标
```

约束三条：重试上限 2 次；只能重跑白名单内的节点（统计检验、异常、图表）；每次重试的决策必须写入事件轨迹。

这一步让「流程长度由模型决定」成立，是形态上最实质的跨越。但它会显著增加复杂度与调用次数，建议在计划层稳定后再做。

## 五、可复现性设计

### 5.1 四项措施

**其一，数值不经过模型。** 计划里只有选择，没有结果。异常阈值、变化点判据这类统计结论由 dev 段标定，明确列入 `constraints` 禁止模型修改。

**其二，温度 0 与固定 seed。** 降低输出的随机性，但不承诺完全确定——这是诚实的表述。

**其三，计划缓存。** 二次运行直接命中，端到端结果必然一致。这才是可复现的真正保障，而不是指望模型稳定。

**其四，计划即证据。** 计划写入 result.json，任何人可以复现「当时为什么这么分析」。

### 5.2 指标口径调整

原有「重复运行一致率」检验端到端结果一致。引入模型后需拆成两条，否则该指标会因模型的微小波动而不稳定，进而掩盖真实问题。

**表 5-1 指标拆分**

| 指标 | 口径 | 阈值 | 说明 |
| --- | --- | --- | --- |
| 重复运行一致率 | **同计划**下执行结果完全一致 | 必须 1.00 | 守住可复现的实质 |
| 计划一致率 | 同输入两次规划，计划是否相同 | 如实报告，不设阈值 | 反映模型的确定性程度 |
| 计划合法率 | LLM 输出通过三级校验的比例 | 不低于 0.95 | 衡量提示词与 schema 质量 |
| LLM 回退率 | 回退到规则的比例 | 不高于 0.20 | 超过说明接入有问题 |

前一条是硬指标，后三条是观测指标。**把「计划一致率」设为观测而非验收**，是因为它本质上取决于模型服务，不应成为项目验收的否决项。

### 6.1.1 M1 实际落地与实测

M1 已实现并接入，用 DeepSeek（`deepseek-chat`）实跑验证。落地过程中暴露了两个原方案未预见的问题，一并记录。

**问题一：工具名与下游消费点不一致（已修复）**

初版工具集按「分析大类」命名（`correlation`、`stat_tests`、`volatility`），而引擎实际判断的是 `corr`、`test`、`stationarity` 等细粒度名。后果不是报错，而是**静默失效**：模型选 `correlation` 能通过白名单校验、写进 `analyses`，但没有任何模块认这个名字，对应分析一项都不跑——计划看起来成功，结果却是空的。

修正为下游真实的 13 个名字，并加了一条一致性测试：工具名集合必须等于下游消费点集合，以后改名字漏改下游会立即失败。

**教训**：凡是「模型输出 + 下游消费」的接口，名字对不上不会报错，只会安静地什么都不做。这类失效必须用断言锁死，不能靠人工核对。

**问题二：配置不全时静默回退（已修复）**

`MTSA_LLM_BASE_URL` 与 `MTSA_LLM_API_KEY` 中任意一个缺失，`build_planner` 都会直接返回规则计划器且不留痕迹。用户配了密钥却漏了 URL，运行时看到的是「成功」和 `plan_source=rule`，很容易误以为模型没生效是模型的问题。

现在区分三种情形：

| 情形 | 行为 |
| --- | --- |
| 两个都没配 | 静默走规则（这是默认用法，不打扰） |
| 配了一半 | 回退规则，并把「缺少哪个变量」写入 `result.warnings` |
| 显式 `MTSA_PLANNER=llm` 却没配 | 同样回退，并在 warnings 点名两个变量都缺 |

**实测结果**

| 项目 | 结果 |
| --- | --- |
| 首次运行 | `plan_source=llm`，耗时 25 秒，warnings 为空 |
| 模型选中分析项 | `trend`、`seasonal`、`extreme`（3 项；规则计划默认 12 项） |
| 第二次同问运行 | `plan_source=cache`，分析项完全相同，未重复调用模型 |
| 产物完整性 | 7 组图、报告、结构化结果、复现脚本均正常生成 |
| 既有指标 | 22 项全过，其中原 21 项数值与改造前逐位一致 |
| 测试 | 126 项全过（新增 3 项配置诊断测试） |

**一个必须说明的差异**：模型选出的分析项明显少于规则计划（3 项对 12 项）。这是「由模型决定范围」的必然结果，不是缺陷——模型按问题只选了相关分析。但使用时要意识到：LLM 模式下的报告覆盖面会小于规则模式。若需要完整分析，应在问题里明确要求，或直接使用规则模式。

### 6.2 第二步：有界重试（M2）

| 项目 | 内容 |
| --- | --- |
| 目标 | 证据校验失败时由模型决定重跑，流程长度可变 |
| 改动 | engine 主循环、节点白名单、重试计数与留痕 |

> **本节已被取代。** 复核后认为 M2 的目标偏窄：它只覆盖「出错后纠错」，而 Agent 的实质是「根据中间结果决定下一步」。真正的改造需要让模型在执行过程中观察并决策，M2 的重试能力被吸收进自主循环，不再单列。
>
> 后续实施已重排为 T2.1 至 T2.10，详见 `doc/agent化任务清单.md`。该清单同时界定了改造范围——数据管道（导入至清洗）与收尾（图表至报告）固定，仅分析层六项可由模型自主编排。

### 6.3 第三步：工具自主选择（M3）

当前工具集是固定的八项，模型只做子集选择。若要让模型真正「发现」工具，需引入工具注册机制：适配器可注册新工具，模型从动态清单中选择。

这一步价值最高但风险也最高——模型可能选择不适用的工具，产生无意义结论。建议在 M1 与 M2 稳定、且评估指标有富余后再考虑。

> **本节的工具注册机制已并入 T2.1**（分析层工具化建立注册表）与 T2.4（决策安全边界限制可选范围）。不再作为独立阶段。

## 七、测试计划

### 7.1 单元测试

不依赖真实模型，全部用 MockPlanner 与桩客户端。覆盖四类：正常路径、校验失败、超时与异常、无配置回退。

关键约束：**测试不得因缺少 API key 而跳过或失败**。无 key 是常态而非异常，必须能在无网络环境下完整运行。

### 7.2 集成测试

用真实数据（fixtures 中的天气样例）跑完整流水线，分别验证 `MTSA_PLANNER=rule` 与 `mock` 两种模式，断言：

- 两种模式下 result.json 的结构完全一致
- `plan_source` 字段正确
- 计划缓存命中时不再发起网络请求（用桩客户端计数断言）

### 7.3 评估指标

| 指标 | 获取方式 | 是否阻断 |
| --- | --- | --- |
| 计划合法率 | 评估脚本统计 | 是（不低于 0.95） |
| LLM 回退率 | 同上 | 是（不高于 0.20） |
| 计划一致率 | 同输入重复规划 | 否，仅报告 |
| 重复运行一致率 | 同计划执行两次比对 | 是（必须 1.00） |

## 八、风险与对策

**表 8-1 风险清单**

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 模型输出不稳定 | 两次运行计划不同 | 计划缓存；计划一致率如实报告不设阈值 |
| 模型编造工具或列 | 执行失败或结果无意义 | 三级校验中的语义校验直接拦截 |
| 服务不可用 | 流水线中断 | 兜底链四级递进，最终回落到最小可用计划 |
| 延迟增加 | 单次分析变慢 | 只调用一次；输入仅摘要；缓存命中时零延迟 |
| 成本失控 | 调用费用不可控 | 输入不含原始数据；只在计划阶段调用 |
| 评审口径变化 | 形态归属仍有争议 | 在报告中如实声明「受控 Agent」并给出四项证据 |

## 九、验收标准

M1 完成后，需同时满足以下六条：

| 序号 | 标准 | 判定 |
| --- | --- | --- |
| 1 | 存在一条由模型决定计划的执行路径 | plan_source 可为 llm |
| 2 | 无模型配置时系统完整可用 | 109 项既有测试全通过 |
| 3 | 模型输出不合规时有明确回退 | 六项测试覆盖 |
| 4 | 计划的来源与内容可审计 | result.json 含 plan 与 plan_source |
| 5 | 同计划下结果可复现 | 重复运行一致率 1.00 |
| 6 | 计划层改动未影响任何数值结论 | 21 项评估指标数值与改造前一致 |

第 6 条最关键：改造只应改变「选择」，不应改变「结果」。若某项指标数值发生变化，说明改造越界了，必须回退排查。

## 十、附录

### 10.1 计划的 JSON Schema 要点

```
{
  "scene_id": "weather | stock",
  "analyses": ["trend", "anomaly", ...],        // 必须是八项工具的子集，至少一项
  "target_columns": ["temperature@STA_A", ...], // 必须存在于实际数据
  "parameters": {                                // 仅允许白名单键
    "seasonal_period": 24,
    "max_lag": 48,
    "rolling_window": 20
  },
  "reason": "选择理由，供审计"                     // 必填，不可为空
}
```

`reason` 必填是刻意的：模型必须说明为什么选这些工具。这条要求既提升计划质量，也让审计有据可查。

### 10.2 提示词草案要点

系统提示需固定四段内容：可用的八个工具及适用条件；数据摘要的字段含义；输出必须为 JSON 且符合 schema；不得修改的字段清单。

用户消息只放问题与数据摘要，不放任何示例计划——示例会让模型倾向模仿，降低对数据特征的响应度。

### 10.3 改造前后对照

**表 10-1 形态对照**

| 维度 | 改造前 | 改造后（M1） | 改造后（M2） |
| --- | --- | --- | --- |
| 流程决定权 | 代码 | 代码 | 模型（有界） |
| 工具选择权 | 规则 | **模型** | 模型 |
| 模型参与度 | 无 | 计划阶段一次 | 计划 + 重试判断 |
| 终止条件 | 固定十二节点 | 固定十二节点 | 模型判断或超限 |
| 可复现性 | 天然可复现 | 靠缓存保证 | 靠缓存 + 计划留痕 |
| 形态归属 | pipeline | **受控 Agent** | Agent |

M1 完成后即可主张「模型根据状态动态选择工具」，这是规范的原文要求。M2 完成后，「流程由模型决定」也成立，形态争议基本消除。
