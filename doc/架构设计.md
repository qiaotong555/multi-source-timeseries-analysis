# 架构设计

## 1. 定位

`multi_source_timeseries_analysis`（课题 12 / S06）是一个**通用时序分析引擎 + 场景适配器**。引擎与场景解耦：引擎负责与业务无关的数据导入、质量检查、预处理、时域/频域指标、统计检验、异常与变化点检测、图表与报告；场景适配器只负责「字段角色映射、分析计划、专属指标、专属图表、结论措辞」。

## 2. 分层结构

```text
输入文件（只读）
    │
    ▼
[1] io_loaders      多格式导入（CSV/Excel/Parquet/NPY/MAT/HDF5）→ RawDataset
    ▼
[2] profiler        时间轴与变量角色识别、字段与采样摘要 → DatasetProfile
    ▼
[3] quality         缺失/重复/乱序/异常值/采样不连续 → QualityReport
    ▼
[4] planner         结合场景适配器与自然语言问题 → AnalysisPlan
    ▼
[5] preprocess      去重排序、重采样、插值、标准化、滤波、去趋势 → CleanDataset
    ▼
[6] metrics         时域指标（趋势/波动/相关/滞后相关/极值）→ MetricTable
    [7] spectrum    FFT / 功率谱 / 时频图 → SpectrumResult
    [8] stats_tests ADF、KPSS、Ljung-Box、Jarque-Bera、Mann-Kendall、卡方、游程
    [9] anomaly     异常点（滚动 Z、MAD、STL 残差）与变化点（均值/方差突变）
    ▼
[10] viz            Plotly 静态图（PNG）+ 交互图（HTML）→ Artifact[]
    ▼
[11] report         结论生成 + 结论—证据绑定 → report.md / report.html
    ▼
[12] verify         数值复算与图表字段映射校验；失败则按计划重跑（最多 2 次）
```

节点 [1]~[12] 由 `src/mtsa/engine.py` 的确定性状态机顺序驱动。每个节点有固定输入/输出 schema、固定耗时记录与固定事件名，写入 `events`。

### 2.1 计划层

节点 [4] 的「计划」由 `src/mtsa/planner.py` 产出，有两种实现：

| 实现 | 触发条件 | plan_source |
| --- | --- | --- |
| RulePlanner | 未配置 LLM，或显式 `MTSA_PLANNER=rule` | `rule` |
| LLMPlanner | 已配置端点与密钥 | `llm`（首次）/ `cache`（命中缓存） |

LLM 计划的产出必须通过三级校验：格式（能否解析为 JSON）、schema（必填字段与非空列表）、语义（工具名在白名单、列真实存在、参数不越界）。任何一级失败即回退规则计划，回退原因写入 `warnings`，计划来源写入 `result.json` 的 `data.plan.plan_source`。

兜底链为「缓存 → LLM → 规则」，规则计划永远可用。这样设计的原因：计划层把一个不确定的外部服务引入了原本确定的流水线，若不设兜底，一次网络抖动就会让整次分析失败。

**硬边界：模型只决定「选择」，不决定「结果」。** 计划里只有选哪些工具、分析哪些列、什么窗口，没有任何数值；异常阈值与变化点判据属统计标定结果，列入禁止修改清单。判据是评估指标：改造前后 21 项指标数值必须完全一致，若发生变化说明改造越界。

完整改造方案（含 M2 有界重试、M3 工具自主）见 `doc/agent化改造方案.md`。

## 3. 为什么不用 LangGraph（环境偏差说明）

规范对 AI for Science 类推荐 LangGraph。本实现使用**确定性状态机**，原因与替代保证：

1. 本课题的全部节点都是确定性计算；引入图框架不产生行为差异，只增加依赖面。
2. 本机环境为 Anaconda base **Python 3.12**（课程建议 3.11），`langgraph==1.2.4` 与当前 pandas/numpy 组合未经课程基线验证，强行引入会扩大不可控面。
3. 状态机节点边界与 LangGraph 节点一一对应（节点名、输入 schema、输出 schema 均已在 `接口与字段.md` 固定），后续接入 LangGraph 只需把节点函数注册为图节点，不改动任何计算代码。
4. LLM 节点（自然语言问题 → 分析计划）在未来规划 T2 中接入；接入后同样只需替换 `planner` 节点实现。

**结论**：这不是降低要求，而是把「工作流编排」与「数值计算」解耦。规范要求的「工具边界、状态、停止条件、权限」在状态机中同样显式存在（见下节）。

## 4. 状态、停止条件与权限

| 项目 | 约束 |
| --- | --- |
| 任务状态 | `queued / running / waiting_for_input / cancel_requested / succeeded / failed / cancelled`，不另设同义状态 |
| 最大重跑次数 | `MAX_RERUN = 2`（校验失败后按修订参数重跑，超过即 `failed`） |
| 最大工具调用数 | `MAX_TOOL_CALLS = 64` |
| 单节点超时 | `NODE_TIMEOUT_SEC = 120` |
| 文件权限 | 输入只读；写入仅限 `artifacts/<run_id>/`；禁止写入输入目录 |
| 人工确认 | 写入、删除、发送、支付、执行外部代码必须经人工确认；本引擎不提供此类工具 |
