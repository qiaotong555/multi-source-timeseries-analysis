# 架构设计

## 1. 定位

`multi_source_timeseries_analysis`（课题 12 / S06）是一个**通用时序分析引擎 + 场景适配器**。引擎与场景解耦：引擎负责与业务无关的数据导入、质量检查、预处理、时域/频域指标、统计检验、异常与变化点检测、图表与报告；场景适配器只负责「字段角色映射、分析计划、专属指标、专属图表、结论措辞」。

## 2. 分层结构

```text
输入文件（只读）
    │
    ▼
[1] io_loaders      多格式导入（CSV/Excel/Parquet/NPY/MAT/HDF5）→ RawDataset
    ▼
[2] profiler        时间轴与变量角色识别、字段与采样摘要 → DatasetProfile
    ▼
[3] quality         缺失/重复/乱序/异常值/采样不连续 → QualityReport
    ▼
[4] planner         结合场景适配器与自然语言问题 → AnalysisPlan
    ▼
[5] preprocess      去重排序、重采样、插值、标准化、滤波、去趋势 → CleanDataset
    ▼
[6] metrics         时域指标（趋势/波动/相关/滞后相关/极值）→ MetricTable
    [7] spectrum    FFT / 功率谱 / 时频图 → SpectrumResult
    [8] stats_tests ADF、KPSS、Ljung-Box、Jarque-Bera、Mann-Kendall、卡方、游程
    [9] anomaly     异常点（滚动 Z、MAD、STL 残差）与变化点（均值/方差突变）
    ▼
[10] viz            Plotly 静态图（PNG）+ 交互图（HTML）→ Artifact[]
    ▼
[11] report         结论生成 + 结论—证据绑定 → report.md / report.html
    ▼
[12] verify         数值复算与图表字段映射校验；失败则按计划重跑（最多 2 次）
```

节点 [1]~[12] 由 `src/mtsa/engine.py` 的确定性状态机顺序驱动。每个节点有固定输入/输出 schema、固定耗时记录与固定事件名，写入 `events`。

### 2.1 计划层

节点 [4] 的「计划」由 `src/mtsa/planner.py` 产出，有两种实现：

| 实现 | 触发条件 | plan_source |
| --- | --- | --- |
| RulePlanner | 未配置 LLM，或显式 `MTSA_PLANNER=rule` | `rule` |
| LLMPlanner | 已配置端点与密钥 | `llm`（首次）/ `cache`（命中缓存） |

LLM 计划的产出必须通过三级校验：格式（能否解析为 JSON）、schema（必填字段与非空列表）、语义（工具名在白名单、列真实存在、参数不越界）。任何一级失败即回退规则计划，回退原因写入 `warnings`，计划来源写入 `result.json` 的 `data.plan.plan_source`。

兜底链为「缓存 → LLM → 规则」，规则计划永远可用。这样设计的原因：计划层把一个不确定的外部服务引入了原本确定的流水线，若不设兜底，一次网络抖动就会让整次分析失败。

**硬边界：模型只决定「选择」，不决定「结果」。** 计划里只有选哪些工具、分析哪些列、什么窗口，没有任何数值；异常阈值与变化点判据属统计标定结果，列入禁止修改清单。判据是评估指标：改造前后 21 项指标数值必须完全一致，若发生变化说明改造越界。

完整改造方案（含 M2 有界重试、M3 工具自主）见 `doc/agent化改造方案.md`。

### 2.2 Agent 运行时（T2.2，仅天气）

T2.2 起，分析层可以切换为由模型逐步选择的自主循环：

```text
固定准备：导入 → 规模 → 摘要 → 质量 → 场景 → 计划 → 清洗
                          ↓
              ┌──── Agent 循环（最多 8 步）────┐
              │ 观察：问题 + 数据概况 + 已完成摘要 │
              │ 决策：选一个白名单工具 / finish    │
              │ 执行：调用工具，summary 回灌       │
              └──────────────┬─────────────────┘
                          ↓
固定收尾：图表 → 报告 → 证据校验 → result.json（含轨迹）
```

**本轮白名单只有五个天气工具**：`compute_metrics`、`analyze_spectrum`、`run_stat_tests`、
`detect_anomalies`、`detect_change_points`。股票专属 `check_lookahead` 不进入白名单；
股票场景请求 Agent 模式直接返回 `AGENT_SCENE_UNSUPPORTED`。

实现位于 `src/mtsa/agent_runtime.py`（`AgentRunner`）。约束：

1. 模型只看到 `ToolResult.summary`，看不到 `data`；
2. `args` 必须为空，参数全部来自计划；阈值等标定参数不可由模型修改；
3. 重复工具、白名单外工具会被拒，拒绝原因回灌；连续越界/连续决策错误会终止；
4. 单个工具失败不抛出循环，记为 `failed` 并写入 `warnings`；
5. 一个工具都没成功执行时整次运行失败（`AGENT_NO_RESULT`），不生成空报告冒充成功。

**观察层**：`src/mtsa/observation.py` 负责生成每一步的上下文——
数据概况（含质量问题计数）、场景与置信度、计划参数、已执行/未执行工具、
计划分析项覆盖情况、最近步骤摘要与较早步骤的一行压缩。
单步约 400 token、总量目标低于 6000 token；超预算时先压缩较早步骤，再压缩最近步骤。
摘要只含统计量与判定，不含原始数据数组。

**安全边界**：`src/mtsa/agent_guards.py` 独立判定动作是否合法——白名单、锁定参数、
未知参数、步数上限、重复调用与失败重试。成功或 skipped 的工具不得重复，
失败工具允许重试一次。每次越界写入 `guard_events`，并按类型累计到 `guard_stats`；
连续越界 3 次终止。边界与运行时分离，便于单独测试，也不会随提示词改动而漂移。

**失败三态**：`tool_states` 区分 `ok`、`skipped`、`failed`、`not_run`。
失败是「试过但没成功」，跳过是「前置条件不满足」，未执行是「模型没选」；
三者都进入 `warnings` 与报告，不能合并成「未发现问题」。

**离线重放**：`src/mtsa/replay.py` 读取 agent 的 `result.json`，用记录里的计划快照与
步骤顺序重跑工具，不调用模型。轨迹哈希覆盖动作、理由、结果摘要，不覆盖耗时与时间戳；
结构化数据除 `agent` 外全部比对。不一致返回 `REPLAY_MISMATCH`——这是 agent 模式下
「可复现」的替代保证：不能指望模型两次走出同一条路径，但可以保证记录下来的路径可重跑。

**模式选择**：CLI 提供 `pipeline` / `agent` / `auto`，优先级为显式参数 > `MTSA_AGENT` > `pipeline`。
`auto` 只在「天气场景 + 模型可用」时升级为 agent，其余情况回退 pipeline 并写入 warning。
默认仍是 pipeline，避免补上模型配置后既有运行方式被悄悄改变。

**与 pipeline 的关系**：pipeline 仍是默认模式，且仍直调底层函数；两条路径共享同一批计算实现。
T2.2 改动后，天气 pipeline 的 `data + conclusions + evidence` 指纹与阶段 0 基线一致
（`3a1eba4c…`），证明没有改变已验证结果。

**已知差异**：Agent 选中某工具时执行该工具的完整分析集，因此统计检验比天气规则计划多 20 条
`chi2_uniform`（`randomness`）。这是「工具完整性优先于计划精简」的当前取舍，后续在 T2.4/T2.10
统一口径。

## 3. 为什么不用 LangGraph（环境偏差说明）

规范对 AI for Science 类推荐 LangGraph。本实现使用**确定性状态机**，原因与替代保证：

1. 本课题的全部节点都是确定性计算；引入图框架不产生行为差异，只增加依赖面。
2. 本机环境为 Anaconda base **Python 3.12**（课程建议 3.11），`langgraph==1.2.4` 与当前 pandas/numpy 组合未经课程基线验证，强行引入会扩大不可控面。
3. 状态机节点边界与 LangGraph 节点一一对应（节点名、输入 schema、输出 schema 均已在 `接口与字段.md` 固定），后续接入 LangGraph 只需把节点函数注册为图节点，不改动任何计算代码。
4. LLM 节点（自然语言问题 → 分析计划）已于 M1 接入，落在 `planner` 节点内，未改动任何计算代码——这正是本条论证的实践验证。详见 `doc/agent化改造方案.md`。

**结论**：这不是降低要求，而是把「工作流编排」与「数值计算」解耦。规范要求的「工具边界、状态、停止条件、权限」在状态机中同样显式存在（见下节）。

## 4. 状态、停止条件与权限

| 项目 | 约束 |
| --- | --- |
| 任务状态 | `queued / running / waiting_for_input / cancel_requested / succeeded / failed / cancelled`，不另设同义状态 |
| 最大重跑次数 | `MAX_RERUN = 2`（校验失败后按修订参数重跑，超过即 `failed`） |
| 最大工具调用数 | `MAX_TOOL_CALLS = 64` |
| 单节点超时 | `NODE_TIMEOUT_SEC = 120` |
| 文件权限 | 输入只读；写入仅限 `artifacts/<run_id>/`；禁止写入输入目录 |
| 人工确认 | 写入、删除、发送、支付、执行外部代码必须经人工确认；本引擎不提供此类工具 |

## 5. Agent 层：实现与边界

分析层可以切换为「观察—决策—行动」循环，范围仅天气场景。各组件职责：

| 组件 | 文件 | 职责 |
| --- | --- | --- |
| 运行时 | `agent_runtime.py` | 组提示词、调模型、执行工具、记录轨迹、token 预算截断 |
| 观察摘要 | `observation.py` | 数据/计划/质量概况；压缩早期步骤；覆盖情况；400/6000 token 预算 |
| 安全边界 | `agent_guards.py` | 白名单、锁定参数、未知参数、步数、重复调用；拒绝事件与统计 |
| 范围下限 | `scope.py` | 按问题关键词推「至少要做什么」；纯函数、无模型、结果可复核 |
| 重放 | `replay.py` | 决策路径哈希；按记录顺序重跑工具；结构化数据比对 |
| 模式选择 | `cli.py` / `engine.py` | `pipeline` / `agent` / `auto`；`auto` 回退写 warning |

**硬约束**：模型只选工具，不产出数值；工具参数来自计划；失败工具最多重试一次；
未执行/失败/跳过的分析必须在报告与 `warnings` 中显式标注，不能解读为「未发现问题」。

**已知限制**

| 限制 | 影响 | 证据 |
| --- | --- | --- |
| 仅天气场景支持 Agent | 股票请求返回 `AGENT_SCENE_UNSUPPORTED` | `tests/test_engine_agent.py` |
| 报告广度低于 pipeline | free：39 → 26.78（−31.3%）；guided：39 → 31.0（4 用例） | 第 12 轮对照、T2.11 |
| 稳定性靠构造保证 | 步数下界=关键词下限、上界=下限+1；换模型或改词表需重测 | T2.11 |
| 端到端未更快 | 墙钟 +4.7%，图表/报告是固定成本 | 第 12 轮对照 |
| 输出不稳定（free） | `free` 模式仍会漂移（跨批次 3 ↔ 5）；`guided` 默认已消除 | T2.8 / T2.9 历史，T2.11 对照 |
| token 预算依赖服务端 usage | 服务端不返回 usage 时预算不生效（标 `unavailable`） | T2.13 真实验证 |
| 覆盖率≠正确性 | 只说明分析是否执行 | `doc/评估设计.md` 6.5 |

## 7. 目录

```text
multi_source_timeseries_analysis/
├── AGENTS.md
├── README.md
├── src/mtsa/            引擎实现
│   ├── engine.py        确定性状态机（节点编排）
│   ├── planner.py       计划层：规则 / 模型双实现
│   ├── llm_client.py    OpenAI 兼容客户端（零依赖）
│   ├── timeout_guard.py 进程级超时保护（父进程侧）
│   └── worker.py        子进程入口（供 timeout_guard 调用）
├── tests/               单元测试与回归测试
├── evals/               评估脚本与评估记录
├── fixtures/            固定脱敏样例与真值标签
├── artifacts/           运行产物（按 run_id 隔离）
├── spec/                当前任务、未来规划、已完成任务、Bug
└── doc/                 架构、接口与字段、评估设计、使用手册
```

**为什么超时要做成独立模块而非写进状态机**：Python 无法中断正在执行的 C 扩展调用，
状态机内的计时器对「节点不返回」这种情况无效。进程隔离是唯一有效手段，因此独立成
`timeout_guard` + `worker`，`run_analysis` 保持原样，库调用者不受影响。
