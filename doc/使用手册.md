# 使用手册 · 多源时序数据量化分析与可视化 Agent

## 安装

```bash
pip install mtsa-agent   # 从 PyPI 安装（发行名 mtsa-agent，命令名 mtsa）
pip install .            # 或在仓库根目录从源码安装
pip install -e .         # 开发用：改 src 立即生效
```

面向使用者的完整说明（Python 版本、数据格式、错误对照表、Docker）见 **`doc/安装与首次运行.md`**。
镜像定义在 `Dockerfile`；本机无 Docker，**未在本机构建**，但 CI 的 `docker` job 已实际构建并跑通（构建 → `list-scenes` → 容器内一次真实分析）。

## HTTP 接口（薄壳）

给别人用时不必 `git clone`：装 `[api]`、起一个服务，提交 → 轮询 → 取产物。
返回的 `result.json` 就是 CLI 那份，**没有第二套 schema**。

```bash
pip install "mtsa-agent[api]"
export MTSA_API_TOKEN=dev          # PowerShell: $env:MTSA_API_TOKEN='dev'
mtsa-api --host 127.0.0.1 --port 8000
```

```bash
# 0) 存活（不鉴权，只回报版本与在跑数量）
curl http://127.0.0.1:8000/healthz

# 1) 先预演：只出计划、不写文件、不跑检测器（就是 CLI 的 --dry-run）
curl -s -H "X-API-Token: dev" -H "Content-Type: application/json" \
  -d '{"input_path":"fixtures/weather_v1.csv","question":"分析温度的趋势、季节性和异常点"}' \
  http://127.0.0.1:8000/api/v1/preview

# 2) 提交（202，立刻返回 run_id；分析在后台子进程里跑）
curl -s -H "X-API-Token: dev" -H "Content-Type: application/json" \
  -d '{"input_path":"fixtures/weather_v1.csv","question":"分析温度的趋势、季节性和异常点","mode":"pipeline"}' \
  http://127.0.0.1:8000/api/v1/analyses

# 3) 轮询：queued → running → succeeded / failed
curl -s -H "X-API-Token: dev" http://127.0.0.1:8000/api/v1/analyses/<run_id>

# 4) 取结果与产物
curl -s -H "X-API-Token: dev" http://127.0.0.1:8000/api/v1/analyses/<run_id>/result
curl -s -H "X-API-Token: dev" -o report.md \
  http://127.0.0.1:8000/api/v1/analyses/<run_id>/artifacts/report.md

# 5) 上传（数据不必先放到服务器上）
curl -s -H "X-API-Token: dev" -F "file=@local.csv" -F "question=分析温度趋势" \
  http://127.0.0.1:8000/api/v1/analyses/upload
```

| 路由 | 作用 |
| --- | --- |
| `GET /healthz` | 存活与版本；**不鉴权**，不含任何数据 |
| `POST /api/v1/preview` | 同步预演：字段摘要 + 场景 + 计划 + 将要调用的工具 |
| `POST /api/v1/analyses` | 提交（JSON，服务端路径）→ 202 + `run_id` |
| `POST /api/v1/analyses/upload` | 提交（multipart 上传文件）→ 202 + `run_id` |
| `GET /api/v1/analyses/{run_id}` | 状态信封：状态、耗时、错误、产物清单、`result_url` |
| `GET /api/v1/analyses/{run_id}/result` | 原样返回那次运行的 `result.json` |
| `GET /api/v1/analyses/{run_id}/artifacts/{name}` | 下载白名单内的产物（`report.md`、图、`clean_data.csv`…） |

**不想敲 curl**：浏览器打开 `http://127.0.0.1:8000/docs`——FastAPI 自动生成的接口文档，
每个接口的 `X-API-Token` 直接填在表单里，点 Execute 就能提交与查看响应。
（浏览器直接访问 `/api/v1/...` 会 401：请求头得由客户端带，不是浏览器的功能。）

注意 `input_path` 是**服务端**路径，由服务进程的工作目录解析；`upload` 的 `file=@...` 是
**客户端**路径。两边不在同一个目录时，前者相对服务端、后者相对你的 shell。

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `MTSA_API_TOKEN` | 无 | **必填**；缺失时 `mtsa-api` 直接退出（默认无鉴权等于没门） |
| `MTSA_API_WORKERS` | 2 | 并发执行的分析数 |
| `MTSA_API_QUEUE` | 32 | 排队上限，满了返回 429 + `Retry-After: 30` |
| `MTSA_API_RUN_TIMEOUT` | 300 | 单次分析硬超时（子进程被杀，返回 `NODE_TIMEOUT`） |
| `MTSA_API_MAX_UPLOAD_MB` | 50 | 上传上限，超了 413 且不留下半截文件 |
| `MTSA_API_OUT` | `./artifacts/api` | 产物根目录；按当前工作目录解析（容器里是 `/data/artifacts/api`） |

**边界（有意为之，不是没做完）**

1. 不做业务逻辑：不判场景、不映射参数、不改 `result.json` 契约；
2. 不做持久化：运行状态在进程内，重启后 `GET` 返回 404（产物仍在 `artifacts/api/<run_id>/`）；
3. 不做取消、不做流式、不做多租户——`cancel_requested` / `waiting_for_input` 仍是空词表；
4. 请求体不接受 `output_dir` / `replay_from` / `price_table`：这三个都是服务端路径；
5. 每次运行多约 3 秒子进程启动开销，换来「跑飞了能杀掉」；
6. 单 token 不是用户体系：所有调用方共享一个身份。

## 运行保护

| 限制 | 默认 | 调整方式 |
| --- | --- | --- |
| 数据规模 | 20 万行，超过即拒绝（`DATASET_TOO_LARGE`） | `MTSA_MAX_ROWS=500000` |
| 整体超时 | 600 秒，超时终止子进程（`NODE_TIMEOUT`） | `--timeout 900`；`0` 表示不限制且不进子进程 |
| 运行模式 | 默认 `pipeline` | `--mode agent` / `--mode auto`，或设置 `MTSA_AGENT` |
| 计划器 | `auto`：配了模型就由模型出计划（命中缓存复用），没配模型用规则计划 | `MTSA_PLANNER=rule` 固定 12 项规则计划；`llm` 强制走模型、失败回退规则 |
| Agent 范围策略 | `guided`：按问题关键词定下限，达标前不得结束，下限外最多追加 1 步 | `--agent-scope free` 恢复“范围完全由模型决定”（步数会波动） |
| Agent token 预算 | 0（不限制），只记录用量 | `--agent-max-tokens 2000`；超限以 `token_budget` 结束 |

CLI 默认在**子进程**中执行分析：Python 无法中断正在执行的 C 扩展调用（numpy、statsmodels），
主线程计时器拦不住卡死，只有进程级终止有效。代价是约 3 秒启动开销。
库调用 `engine.run_analysis()` 不走子进程，行为与以前一致。

**判断成败请读 `result.json` 的 `status`，不要以「产物目录非空」为准**——失败时也会落盘留档。

评估口径：异常检测阈值只在各折 dev 段上选定，指标取各折 holdout 段平均；有效折不足时判为「不可判定」而非通过，详见 `doc/评估设计.md` 第 3 节。

数据集分工：`weather_v1` 用于交付演示与其余指标，`weather_eval_v1` 专用于异常检测的 dev/holdout 评估（异常密度更高，每折 holdout 约 12 个真值）。两者分离，避免在同一套数据上调参又报告。

产物写入 `artifacts/<run_id>/`：`result.json`（结构化结果与证据链）、`report.md`、
静态图 PNG、交互图 HTML、清洗后数据 CSV、可复现脚本。

**分析项 12 / 13 / 14 的口径**（常见混淆点）：

- **12 项**：天气规则计划实际选中的分析项（`trend`、`corr`、`lag`、`extreme`、`spectrum`、
  `changepoint`、`anomaly`、`test`、`stationarity`、`autocorr`、`normality`、`seasonal`）；
- **13 项**：计划层 `TOOL_SPECS` 在 12 项基础上多一个 `randomness`；
- **14 项**：引擎内部开关 `ALL_ANALYSES` 在 13 项基础上多一个 `volatility`。

评估里说的「规则计划覆盖率」固定以 **12 项**为分母；「工具覆盖率」以 **5 个白名单工具**为分母；
两者不能互相替代。

**两模式实测（13 个天气用例，`guided`，2026-10-23）**：

| 维度 | pipeline | agent |
| --- | --- | --- |
| 成功 | 13/13 | 13/13 |
| 平均步数 | 5.00 | 2.54 |
| 结论（均值） | 39.00 | 29.92（−23.3%） |
| 需求覆盖率 | 1.00 | 1.00 |
| 规则计划覆盖率 | 1.00 | 0.66 |
| 墙钟（均值） | 12.09 s | 12.77 s（+5.6%） |
| token | 0 | 53,924 |

9 用例时期的数字（结论 −31.3%、墙钟 +4.7%）保留在 `doc/评估设计.md` 6.5/6.6，
**不同用例集的降幅不可直接比较**。现行口径见 6.8，逐用例数据见
`evals/mode_compare_results.json`。

**结论级评估（A/B，2026-10-23）**：在这份演示数据上，异常点级 P/R/F1 为
0.130 / 1.000 / 0.229（真值 18、FP 121）；agent 只在 7/13 个用例执行异常检测，
未执行的 6 个用例少看 108 个真值实例，但去重后真值命中仍为 18/18。两模式结论
总数 507 vs 389，差 118 条（9.08/用例），**100% 归因于 `tool_not_run`**，无法归因 0 条。
这说明 Agent 的差异主要是范围而不是精度；也说明「检出 139 个」不等于「139 个都对」。

**探针与重复（D，2026-10-23）**：6 个探针下，free 30 次全部 5 步、39 条结论，
单次平均 7,030 token；guided 6 次平均 2.17 步、3,475 token，范围下限 6/6 达标。
free 本批没有低频抖动，但 30 次同批不能替代跨版本结论；`p_compare_station` 有
3/5 次触发 6,000 token 上限。计划卡「guided/free 各 5 次共 60 次」与「总≤30 次」
矛盾，本轮取 free 30 + guided 6 = 36 次，取舍见 `spec/archive/项目承接已完成.md` 第 26 章。

结论：Agent 适合窄问题与需要审计路径的场景；需要完整报告、或没有模型配额时用 pipeline。

## 边界

- 输入文件只读，从不修改、移动或删除。
- **多站点（长表 + `group_columns`）为正式支持场景**：清洗按实体分组，判重按 `(实体, 时间)`。
- 股票场景不提供真实投资建议，不做自动交易；回测不含交易成本与滑点，结论中显式声明。
- 不做彩票中奖号码预测；彩票场景不在当前任务范围。
- 数值结论全部由计算代码产出，模型不参与任何数值计算。LLM 只参与两处选择：计划层选择分析项，
  以及 Agent 模式选择下一步调用哪个工具。未配置模型时，pipeline 仍可用规则计划运行。
- **Agent 模式本轮只支持天气场景**；股票场景请求 `--mode agent` 会返回 `AGENT_SCENE_UNSUPPORTED`。
  Agent 只决定「调用哪些工具」，工具的完整产出与未执行项都会写入 `result.json` 与报告。
- 对外 REST 服务不在当前任务范围，见 `spec/未来规划.md`。
