## 1. 它是什么

**能回答的问题**

- 这份数据的结构是什么？时间轴连不连续，有没有缺失、重复、乱序、单位异常？
- 趋势方向、季节振幅、峰谷月份、主周期是多少？
- 哪些时刻是异常点、哪些区段是持续异常、变化点在哪里？
- 各列之间是否相关、是否存在滞后关系？
- 在给定假设下，下一个周期（默认 24 小时）大致是什么范围？（`--forecast`，仅天气）
- 结果能否复现？每条结论对应哪个数字、哪个文件、哪一行代码？

**明确不做**

- 不做因果推断，不做交易建议与自动交易；
- 不让模型参与任何数值计算（模型只决定「先跑哪个工具」）；
- 不改原始输入文件，所有产物写入独立 `artifacts/<run_id>/`；
- 股票场景只支持固定流水线，Agent 未实现（请求返回 `AGENT_SCENE_UNSUPPORTED`）；
- 彩票 / CSI 场景、多模型对比、对外 REST 服务，均未实现。

### 两种运行模式

| 模式 | 行为 | 无模型时 |
| --- | --- | --- |
| `pipeline`（默认） | 固定流程、逐节点执行；分析哪些项由计划器决定（规则计划为 12 项） | 正常 |
| `agent` | 天气场景下由模型在白名单 5 个工具里选下一步 | `AGENT_UNAVAILABLE` |
| `auto` | 天气且有模型才升级，否则回退 | 回退 pipeline 并写 warning |

**两个开关不要混**：`--mode` 决定「谁决定执行顺序」，`--planner`（或环境变量 `MTSA_PLANNER`）决定「分析哪些项」。

| 开关 | 控制什么 | 默认 | 改变方式 |
| --- | --- | --- | --- |
| 运行模式 | 固定流水线 / 模型选工具 | `pipeline` | `--mode agent`、`--mode auto`，或 `MTSA_AGENT` |
| 计划器 | 分析项清单由谁给出 | `auto`：配了模型就由模型出计划（命中缓存则直接复用），没配模型用规则计划 | 按请求 `--planner rule` / `llm` / `auto`（HTTP 同理传 `planner`）；或按部署设 `MTSA_PLANNER`。请求优先于环境变量 |

因此「pipeline 固定 12 项、结果确定」只在计划器为 `rule` 时成立。2026-10-25 实测：
同一份天气数据、同一问题，缺省参数下 `plan_source=llm`、只跑 **3 项**；
加 `--planner rule`（或 `MTSA_PLANNER=rule`）才是 **12 项**。要逐位复现，请显式指定。

## 2. 一条链路的六个步骤

| 阶段 | 做什么 | 由谁决定 |
| --- | --- | --- |
| ① 体检 | 时间轴连续性、缺失、重复、乱序、量级与单位；只报告，不自动改数据 | 固定 |
| ② 计划 | 分析项、目标列、周期、阈值 | 规则；或模型选择（agent） |
| ③ 清洗 | 插补 / 丢弃 / 单位换算，动作逐条记账 | 固定 |
| ④ 分析 | 指标、频谱、统计检验、异常、变化点、极端值、泄漏检查 | pipeline 固定；agent 由模型选工具 |
| ⑤ 结论 | 把数字写成一句话，绑定证据（指标名 / 产物编号 / 计算位置） | 固定 |
| ⑥ 报告 | `result.json` + `report.md` + 图表 + 清洗数据 + 复现脚本 | 固定 |

**三个容易混的口径**：规则计划选中 **12 项**分析；计划层 `TOOL_SPECS` 有 **13 项**（多 `randomness`）；引擎内部 `ALL_ANALYSES` 有 **14 项**（再多 `volatility`）。评估里的「规则计划覆盖率」固定以 12 项为分母，「工具覆盖率」以 5 个白名单工具为分母，两者不可互换。

**一条必须记住的口径**：`agent` 比 `pipeline` 少 23.3% 的结论，**100% 归因于「工具未执行」**，不是算错；但「没跑」也不能当成「没问题」——报告里必须写「未执行」，不能写「未检出」。

**R13 为什么定为「能力边界」而不是「待补缺口」**（2026-11-01）：三个实验——同期分位、降分位加持续性、异常通道的窗口×阈值 36 组网格——均未找到「覆盖达标且误报可接受」的参数组合。能达标的组合要求把 **23%–39%** 的观测判为异常（基线异常率 0.3%），即靠牺牲判别力换召回。根因是逐点稳健 Z 判据与真实灾害形态不匹配：灾害多为持续数天的区域高温/寒潮，不是单点离群；而持续高温会被滚动中位数吸收、短暂寒潮不会被吸收，于是同一站位 22 个温度异常点**全部指向低温方向、0 个高温**（方向性偏置，见报告第三节）。

因此本项目明确：**能检出的是统计异常，不是灾害事件**。若未来要做灾害事件检测，那是另一套方法（多尺度残差 / 持续段判据），必须先用同一标尺离线验证「异常率 ≤2% 下能否达到 7/14」，做不到就不立项。

## 5. 交付物与入口

### 运行

```bash
# 安装：pip install .（Python >= 3.12）；开发用 pip install -e .
# 未安装时也可用 PYTHONPATH=src
python -m mtsa.cli run --scene weather \
  --input fixtures/weather_v1.csv \
  --question "分析温度的趋势、季节性和异常点，并检测变化点"

python -m mtsa.cli run --mode agent --scene weather \
  --input fixtures/weather_v1.csv --question "分析温度的趋势、季节性和异常"

python -m mtsa.cli run --scene weather --input fixtures/weather_eval_v2.csv \
  --question "分析温度的趋势" --forecast --forecast-horizon 24

python -m mtsa.cli run --dry-run --scene weather --input fixtures/weather_v1.csv \
  --question "分析温度的趋势"      # 只预演：字段摘要 + 场景 + 计划 + 工具，不写盘

python -m mtsa.cli run --replay artifacts/<run_id>/result.json   # 离线重放，不调模型

# 要逐位复现（规则计划 12 项、不调模型），给这次运行指定计划器：
python -m mtsa.cli run --scene weather --input fixtures/weather_v1.csv \
  --question "分析温度的趋势" --planner rule
# （也可以按部署设置：bash 用 export MTSA_PLANNER=rule，PowerShell 用 $env:MTSA_PLANNER='rule'）
```

**判断成败看 `result.json` 的 `status`，不要以「产物目录非空」为准**——失败时也会落盘留档。

## 10. 反馈与贡献

这个项目最需要的外部输入是「**你算错了**」，不是「做得不错」。

- **结论可疑** → [开一个结论可疑的 issue](https://github.com/qiaotong555/multi-source-timeseries-analysis/issues/new?template=conclusion-wrong.yml)。模板会追问三件事：跑的命令、`result.json` 里那条结论的原文、你期望的结果与依据。
- **跑不起来** → [运行问题](https://github.com/qiaotong555/multi-source-timeseries-analysis/issues/new?template=run-error.yml)。先跑 `mtsa demo --out mtsa-check`：它能跑通说明环境没坏，问题在输入或参数。
- **想知道能信到什么程度** → 先看第 4 节「还没做到」与 `doc/使用手册.md` 的能力边界。

改代码前请读 [`CONTRIBUTING.md`](CONTRIBUTING.md)。三条硬规矩：**可复现、带证据、不为好看改评估口径。**

> 这不是客套：真实事件召回只有 1/14，缓慢漂移与持续偏移检不出——这些短板已经写在上面的清单里。指出它们不会冒犯作者，回避它们才会让项目停在演示阶段。
