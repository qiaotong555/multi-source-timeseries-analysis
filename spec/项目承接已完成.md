### 8.3 子任务 C：审查 `tools.py` 未提交修复


它把工具执行时的分析开关扩展为完整集合，但保留原计划中的阈值、窗口和列映射等参数。修复针对的是一个真实的静默失效风险：计划层可能只给出少数分析项，模型已经选择了某个工具，但底层函数因为继续读取精简的 `plan.analyses`，实际只执行该工具的一小部分分析。

当前测试已覆盖：

- 统计工具在精简计划下仍执行 ADF、KPSS/Ljung-Box 等完整检验；
- 扩展分析开关不改变 `anomaly_threshold` 等参数；
- 原计划对象不被修改；
- 异常检测仍使用原计划阈值；
- 工具结果与对应的底层函数结果一致（对 NaN 做规范化比较）。

**审查结论：**

- 修复方向合理，解决的是“工具已调用但分析不完整”的问题；
- 当前不立即提交，因为还需要在 T2.2 中明确“天气 Agent 的工具集合”和“工具内部完整分析”的边界；

### 9.3 行为约定

**入口**

```powershell
python -m mtsa.cli run --mode agent --scene weather `
  --input fixtures/weather_v1.csv `
  --question "分析温度的趋势、季节性和异常"
```

**Agent 循环**

- 准备层（导入 → 规模 → 摘要 → 质量 → 场景 → 计划 → 清洗）仍由引擎固定执行；
- 模型每一步输出 `{"action", "args", "reason"}`，只能从五个工具中选一个或 `finish`；
- 每次工具结果只把 `summary` 回灌模型，`data` 留给代码；
- 收尾层（图表 → 报告 → 证据校验）仍固定执行。

**失败语义**

| 情况 | 结果 |
| --- | --- |
| 没有模型配置 | `AGENT_UNAVAILABLE`，提示缺哪些环境变量 |
| 非天气场景 | `AGENT_SCENE_UNSUPPORTED`，`details.scene` 给出实际场景 |
| 模型直接 `finish`、一个工具都没跑 | `AGENT_NO_RESULT`，失败但保留轨迹 |
| 单个工具失败 | 不中断循环；该工具记为 `failed`，进入 `warnings` |
| 未执行部分工具 | 流程可成功，但 `warnings` 明确写「对应分析为空，不能解读为未发现问题」 |

**结果字段**

`result.json` 的 `data.agent` 包含：`mode`、`model`、`allowed_tools`、`terminate_reason`、`step_count`、`tools_run`、`steps`（含 `action`、`args`、`reason`、`outcome`、`summary`、`elapsed_ms`、`started_at`）、`rejects`、`elapsed_ms`、`max_steps`。

## 10. T2.3 执行记录：观察摘要器

> 执行日期：2026-10-23
>
> 结论：观察层已独立成模块并接入运行时；上下文有单步与总量预算，覆盖情况写入结果与报告。

### 10.1 目标与问题

T2.2 的运行时在 `_user_prompt()` 里直接拼字符串，存在四个问题：

1. 每一步都重复全部历史摘要，步数越多上下文越大；
2. 没有单步与总量上限；
3. 不告诉模型数据质量、场景置信度、计划参数；
4. 不告诉模型「已经覆盖了哪些计划分析项」，容易重复选或过早结束。

### 10.2 实现

新增 `src/mtsa/observation.py`，对外提供：

| 函数 | 用途 |
| --- | --- |
| `estimate_tokens(text)` | 保守 token 估算（CJK 1 字 1 token，其他 3.2 字符 1 token） |
| `coverage_summary(plan, traj, allowed_tools)` | 工具覆盖与计划分析项覆盖 |
| `build_observation(ctx, question, traj, allowed_tools, max_steps)` | 生成受控上下文 |

上下文包含：

- 分析问题；
- 数据概况：场景、置信度、行数、目标列（最多 8 列）、采样、质量问题的数量/级别/代码；
- 计划：分析项与关键参数（只列标定相关参数，排除 `unit_conversions`）；
- 覆盖：已执行/未执行工具、计划分析项覆盖数；
- 较早步骤：一行式摘要（action、outcome、关键计数）；
- 最近 2 步：完整但截断的 `summary`；
- 最近一次被拒原因；
- 下一步指令。

### 10.3 压缩策略

- 列表最多保留 4 项，超出写「…共 N 项」；
- 字符串最长 80 字符；
- 字典最多保留 8 个键；

## 12. T2.5 执行记录：轨迹持久化与离线重放

> 执行日期：2026-10-23
>
> 结论：agent 结果可通过 `--replay` 在不调用模型的情况下重跑；轨迹哈希与结构化数据都能比对，不一致会明确失败。

### 12.1 为什么需要重放

Agent 的路径由模型决定，不能指望两次调用得到同一条轨迹。
因此可复现性必须换一种保证：

```text
保存轨迹 → 重放时不调用模型 → 按原顺序重跑工具 → 比对结果
```

### 12.2 新增模块

`src/mtsa/replay.py`：

| 函数 | 用途 |
| --- | --- |
| `load_replay(path)` | 读取并校验 agent 的 `result.json`，取出计划快照、输入路径、步骤 |
| `trajectory_hash(agent)` | 对决策路径做规范化 SHA-256 |
| `replay_steps(source, ctx)` | 按记录顺序重跑工具，构造新轨迹 |
| `diff_paths(recorded, replayed)` | 返回两份结构化数据的差异路径 |

哈希覆盖：

- 模型名；
- 白名单；
- 每一步的 `action`、`args`、`reason`、`outcome`、`summary`、`error`。

哈希**不覆盖**：

- `elapsed_ms`、`started_at`；
- `run_id`、`request_id`、时间戳；
- `coverage`、`tool_states` 等派生字段。

理由：机器负载会改变耗时，但不改变分析结论；派生字段由轨迹决定，重复计算即可。

### 12.3 引擎接入

`AnalysisRequest` 新增：

```text
replay_from: Optional[str]
```

`run_analysis` 在重放时：

1. 读取记录的 `data.plan`，直接构造 `AnalysisPlan`，**不重新规划**；
2. 仍执行导入、摘要、质量检查与清洗（保证输入数据未变）；
3. 不构造 LLM 客户端，完全跳过模型；
4. 按记录顺序执行工具（包括原轨迹里的重试）；
5. 走与 agent 模式相同的收尾层（图表、报告、证据校验）；
6. 比对轨迹哈希与结构化数据；
7. 写入 `data.agent.replay`。

重放拒绝：

| 情况 | 错误码 |
| --- | --- |
| 源文件不存在 / 非 JSON / 没有 `data.agent` | `REPLAY_INVALID` |
| 用 `--mode pipeline` 重放 | `REPLAY_INVALID` |
| 重放时传 `--param` | `REPLAY_INVALID` |
| 轨迹哈希或结构化数据不一致 | `REPLAY_MISMATCH` |

### 12.4 结果字段

`data.agent` 新增：

| 字段 | 含义 |
| --- | --- |
| `trajectory_sha256` | 本次轨迹的规范化哈希 |
| `replay` | 重放信息：源路径、源哈希、重放哈希、轨迹是否一致、数据是否一致、总是否一致、差异列表 |

`replay.data_match` 比较的是 `data` 中除 `agent` 外的全部结构化内容：
`profile`、`quality`、`plan`、`clean`、`metrics`、`scenario_metrics`、`spectrum`、
`tests`、`anomalies`、`change_points`、`lookahead`，以及 `conclusions`、`evidence`。

### 12.5 用法

```powershell
# 先跑一次 agent
python -m mtsa.cli run --mode agent --scene weather `
  --input fixtures/weather_v1.csv --question "分析温度的趋势、季节性和异常" `
  --output artifacts/run1

```

`--replay` 会自动从原结果读取输入路径与原问题；只有显式传入时才覆盖。

## 13. T2.6 执行记录：双模式并存（pipeline / agent / auto）

> 执行日期：2026-10-23
>
> 结论：三种模式可用；auto 在有模型且场景支持时走 agent，否则回退 pipeline 并写明原因；pipeline 结果与基线完全一致。

### 13.1 模式语义

| 模式 | 行为 | 无模型时 |
| --- | --- | --- |
| `pipeline` | 固定流水线 | 正常 |
| `agent` | 天气场景由模型选择工具 | `AGENT_UNAVAILABLE` |
| `auto` | 有模型且天气 → agent；否则 pipeline | 回退 pipeline，写 warning |

默认仍是 `pipeline`。原因：补上模型配置后，不应让原本的固定流水线运行悄悄变成 Agent。
需要自动选择时必须显式 `--mode auto` 或设置 `MTSA_AGENT=auto`。

### 13.2 环境变量开关

新增 `MTSA_AGENT`：

| 取值 | 解析结果 |
| --- | --- |
| 未设置 / 空 | `pipeline` |
| `off` / `false` / `0` / `pipeline` | `pipeline` |
| `agent` / `on` / `true` / `1` / `yes` | `agent` |
| `auto` | `auto` |

优先级：**显式 `--mode` > `MTSA_AGENT` > `pipeline`**。
这样 `MTSA_AGENT=off` 就是任务书要求的回滚开关，同时不影响显式 CLI。

### 13.3 auto 的判定顺序

`auto` 在清洗完成后判定（此时已知场景）：

1. 重放源存在 → 强制 `agent`（重放不需要模型）；

3. `client_from_env()` 返回 None → `pipeline`，warning「未配置可用的模型客户端」；
4. 其他 → `agent`。

### 15.3 指标口径

| 指标 | 定义 | 本次用途 |
| --- | --- | --- |
| 平均步数 | `step_count` 平均 | 成本与绕路 |
| 终止原因分布 | `terminate_reason` 计数 | 正常结束 / 步数耗尽 / 空转 |
| 工具覆盖率 | 已执行(ok/skipped) / 白名单 5 个 | 白名单利用率 |
| 计划分析项覆盖率 | 已覆盖 / **本次计划**的分析项 | 与计划层对齐 |
| 规则计划覆盖率 | 已覆盖 / 天气规则计划 **12 项** | 广度对照 |
| 需求覆盖率 | 已覆盖 / 该问题明确需要的分析项 | **防过早结束的主指标** |
| 轨迹可重放率 | 重放哈希与结构化数据都一致 | 可复现性 |
| 越界拒绝 | `guard_stats.violations`、rejects 条数 | 安全边界 |
| 工具失败率 | 失败步骤 / 实际尝试步骤 | 稳定性 |
| 耗时 | `data.agent.elapsed_ms` | 性能 |
| token | 服务端 `usage` 累计 | 成本；缺失记 None |

**为什么同时报两条覆盖率。** 规则计划覆盖率的分母固定为 12，窄问题只需 1 项，
用它做验收阈值必然冤枉模型；只看「本次计划」又会被计划层压缩范围掩盖——计划只列 2 项时，
跑 2 个工具就是 100%。因此验收看需求覆盖率，规则计划覆盖率只做广度对照。

### 16.4 结论：Agent 的优点

1. **需求覆盖不降。** 8 个有明确需求的用例，Agent 的需求覆盖率都是 1.00，
   没有因为少跑工具而漏掉问题直接要求的分析项。
2. **窄问题上明显更省。** `wx_normal`（是否正态）只跑 1 步、1 条结论、2,090 token；
   `wx_anomaly` 只跑 2 步。固定流水线在这些问题上仍产出 39 条结论，属于冗余。
3. **路径可审计、可重放。** 轨迹落盘、可离线重跑（T2.8：9/9 重放一致），
   pipeline 虽然确定，但看不到「为什么选这些分析」。

### 16.5 结论：Agent 的劣势

1. **报告信息量下降约三成。** 平均结论 39 → 26.78；窄问题可能只剩 1 条结论
   （`wx_normal`）。对「顺便发现其他问题」这类需求，Agent 明显更弱。
2. **端到端并没有更快。** 虽然平均少跑 1.33 个分析单元，墙钟反而慢 2.4 s（+4.7%）：
   图表与报告是固定成本，模型调用又叠加了延迟。**「少算」≠「更快」**。
3. **广度下降。** 规则计划覆盖率 1.00 → 0.72，四个窄用例只覆盖 0.17–0.58。
4. **输出不稳定。** 同一问题跨运行步数会变（`wx_stationary` 在 T2.8 是 3 步，本轮是 5 步），
   报告篇幅随之波动；pipeline 的 39 条结论每次一致。
5. **有 token 成本。** 9 次共 48,565 token（约 5,396/次）；pipeline 在规则计划下为 0。
   若计划层也用模型，两边都有成本，但 Agent 的调用次数随步数增长。

### 16.6 怎么选

| 场景 | 建议 |
| --- | --- |
| 需要完整体检、报告尽量全 | pipeline |
| 问题很窄、只要结论、在意 token | agent |
| 需要可审计的决策路径 | agent（轨迹 + 重放） |
| 批量离线跑、无模型配额 | pipeline |

默认仍保持 `pipeline`；Agent 需要显式 `--mode agent` 或 `--mode auto`。

### 16.7 限制

- 只有 9 个用例、单模型（deepseek-chat）、单计划层（rule），不构成统计显著性证据；
- 墙钟含图表渲染（约 40 s 量级），换机器或换后端会改变绝对值和差值；
- 覆盖率衡量「分析是否执行」，不衡量检出结果是否正确；
- 需求项由人工标注，标注本身带主观性；探针用例不参与需求覆盖率；
- 本轮没有测多模型、没有测长问题、没有测并发。

## 19. 工程化：低内存测试入口（2026-10-23）

### 19.1 问题

本机内存紧张时，单进程跑全量 pytest 会 CPU 归零、无报错、停在同一位置：
numpy/OpenBLAS 在重试分配内存，pytest 既不失败也不退出。人工只能杀进程重跑，
且不知道卡在哪个文件。

### 19.2 方案

新增根目录 `run_tests.py`：

- 每个测试文件一个独立子进程；
- 每个文件可设超时（默认 900 s），超时杀进程并标记 `STALLED`；
- 固定 `MTSA_PLANNER=rule`、`OPENBLAS_NUM_THREADS=1`，测试不联网、不抢线程；
- 解析 `N passed` 汇总，写 `evals/test_logs/summary.json`。

```bash
python run_tests.py --timeout 300
python run_tests.py --only "test_viz_export.py"
```

### 19.3 结果

```text

测试通过 281，失败 0，错误 0
总耗时 227.0 s
```

对比：单进程全量在内存紧张时会无限卡死；逐文件入口最坏情况也能在
`文件数 × 超时` 内给出明确失败。

### 19.4 实现中踩到的两个坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| `-q` 叠加成 `-qq` | 汇总行消失，统计全为 0 | `build_command` 不再传 `-q`（pyproject 已有） |
| basetemp 父目录不存在 | 全部用例 setup 报 `FileNotFoundError` | 运行前创建 `artifacts/_pt_lowmem/` |

两条都加了测试，防止回归。

### 19.5 限制

- 逐文件启动有固定开销（每个约 1–3 s），全量比单进程多约 1 分钟；
- 超时只杀直接子进程，Windows 下孙进程可能残留（与 #8 同一限制）；
- 汇总依赖 pytest 的 `N passed` 输出格式，升级 pytest 后需复核解析。

## 20. T2.11 执行记录：Agent 输出稳定性（2026-10-23）

### 20.1 问题：同一问题，步数会变

历史证据（两份结果文件都在，可直接复查）：

| 运行 | 文件 | 同一问题 | 步数 | 终止原因 |
| --- | --- | --- | --- | --- |
| T2.8 评估 | `artifacts/t28_agent_eval_real2/wx_stationary/result.json` | 评估这条时间序列是否平稳，并说明其自相关结构 | **3** | `model_finished` |
| T2.9 对照 | `artifacts/t29_compare_real/wx_stationary_agent/result.json` | 同上 | **5** | `model_finished` |

两次运行都成功、都用 `temperature=0`、都走同一白名单，步数却差 2。
这不是随机种子问题，而是**结束条件是主观的**：T2.2 的提示词说
「当你认为已覆盖问题所需的分析时输出 finish」——「所需」由模型每次自行判断，
判断边界漂移，步数就漂移。温度只能降低采样随机性，管不了判断标准。

后果有三条，都是实际影响而不是理论担忧：

1. 同一份数据跑两次，报告结论条数不同（本次实测 26 与 35 同题出现过），
   报告之间无法逐条比对；
2. 成本不可预估：步数直接决定模型调用次数与 token；
3. 「可复现」只做到「轨迹可重放」，没做到「同题同路径」。

### 20.2 方案：把「至少要做什么」外置为规则

新增 `src/mtsa/scope.py`（纯函数，无模型、无 IO）：

- 从**问题关键词**推出下限工具集，`compute_metrics` 恒在下限内（它是报告与结论的底座）；
- 命中词表白盒可查：`平稳/单位根/kpss/自相关/正态/…` → `run_stat_tests`；
  `周期/频谱/主频/功率谱/振荡` → `analyze_spectrum`；`异常/离群/故障` → `detect_anomalies`；
  `变化点/突变/拐点/结构变化` → `detect_change_points`；
- 只为白名单内的工具生成下限，顺序按白名单固定，保证同一问题两次得到同一集合；
- 命中的关键词写进轨迹（`scope.matched`），可人工复核「为什么这一步是必须的」。

运行时（`src/mtsa/agent_runtime.py`）新增两种范围模式：

| 模式 | 范围从哪来 | 结束条件 | 步数 |
| --- | --- | --- | --- |
| `guided`（默认） | 关键词下限 + 模型自行决定顺序 | 下限未覆盖时 `finish` 被拒（`scope_incomplete`）；下限外最多追加 `agent_max_extra_steps`（默认 1）步；超预算立即结束（`budget_exhausted`） | 下限大小 ~ 下限+1 |
| `free` | 完全由模型判断（T2.2 原始语义） | 模型说结束就结束 | 会波动 |

两条边界必须写明：

1. **下限工具彻底失败时允许结束**。若一直拒绝结束，运行会空转到 `max_steps`，
   把「做不到」伪装成「没做完」。现在按「失败且重试用尽」放行，并在
   `scope.met=false` 与 `scope.missing` 里如实记录。
2. **超预算不再反复问模型**。第一版是「拒绝并回灌」，实测模型会在下限外继续尝试，
   连续 3 次拒绝后以 `idle_loop` 结束——步数没变，但白花了 3 次模型调用，
   终止原因还在 `idle_loop` 与 `model_finished` 之间抖。改为预算用尽即结束
   （`budget_exhausted`），终止原因随之确定。预算事件只进 `rejects`，不进 `guard_events`——
   否则「越界次数」会把正常的追加尝试也算成违规。

### 20.6 取舍：拿自主性换可复现

T2.2–T2.9 的卖点是「流程长度由模型决定」。guided 把**范围**的裁量权收走，
只保留**顺序**与**1 步扩展**：

- 保住了：先跑哪个、工具失败后换哪个、要不要为核查矛盾多跑一步；
- 失去了：自由裁剪范围（这正是 T2.9「结论 39 → 26.78」的来源）；
- 代价：结论数比 free 少 8 条（−20.5%），比 pipeline 的 39 少 8 条；
- 收益：步数可预判、成本可预算（token −37.3%）、同题报告可逐条对比。

需要自由探索时仍可用 `--agent-scope free`，但它的结果只能按「单次运行」引用，
不能当作可复现结论。

### 20.7 限制

- 关键词表靠人工枚举，不理解否定与语境（「不需要检验」仍会命中「检验」）。
  错误方向是「多做一步」，不是「少做」，代价是成本而非正确性；
- 下限只保证「覆盖到」，不保证「结论充分」：`compute_metrics` 覆盖趋势/季节/极值，
  但频谱结论仍需 `analyze_spectrum` 才会出现；
- 4 个用例、每组 3 次，样本小；低频抖动只能说 guided 的边界是确定的，
  不能说已经用统计检验证明「绝不会漂移」；
- 结论条数在 guided 下已稳定（本批 0 极差），但换模型或换数据后需重测，
  不能把「deepseek-chat 上稳定」当成普适结论。

## 21. T2.12 执行记录：评估集扩容（2026-10-23）

### 21.1 为什么要扩容

原 9 用例全部围绕「单一需求 + 一次探针」：8 个有明确期望项、1 个开放探针。
它回答不了三类问题：

1. **长问题会不会漏项**：一句话里含 5 个需求时，模型是否只做前两个；
2. **数据质量类问题**：问题指向「缺失和异常」时，是否仍只跑描述统计；
3. **否定/条件表述**：说「如果没有趋势」是否会被误读成「不需要趋势分析」。

另外，9 用例里 8 个是单需求，`mean_need_coverage` 很容易到 1.00，
这个指标在原集合上区分度不足。

### 21.2 新增 4 个用例

## 22. T2.13 执行记录：token 预算（2026-10-23）

### 22.1 问题

T2.8 起只记录 token，不拦截：`max_steps` 限制的是步数，不是成本。
13 用例实测单次 3.2k–7.9k token，长问题或反复试错时没有上限，只能事后看账单。

### 22.2 语义（先定义，后实现）

1. **只约束模型调用**。预算检查在每次决策之前；工具执行不耗 token，
   所以超限前已选中的工具仍会跑完，结果不丢。
2. **`agent_max_tokens=0` 表示不限制**，`budget.enforced=false`，行为与 T2.12 一致。
3. **服务端不返回 `usage`**：`budget.unavailable=true`，运行继续，`warnings` 写明
   「预算未生效」。不按字数估算 token——估算值会变成假账。
4. **`used` 来自客户端 `usage_summary().total_tokens`**，与服务端账单同源。

### 22.3 代码与接口

| 文件 | 改动 |
| --- | --- |
| `src/mtsa/models.py` | `agent_max_tokens: int = 0` |
| `src/mtsa/cli.py` | `--agent-max-tokens N` |
| `src/mtsa/agent_runtime.py` | 循环顶部检查累计用量；终止原因 `token_budget`；`budget` 写入轨迹 |
| `src/mtsa/engine.py` | 透传上限；预算未生效/已截断写 `warnings`；`max_tokens` 进 `data.agent` |

### 22.5 真实运行（deepseek-chat，同一问题）

问题：「分析温度的趋势、季节性与异常，并判断是否平稳」

| 运行 | 上限 | 步数 | 终止原因 | used | 需求下限 | 结论数 |
| --- | --- | --- | --- | --- | --- | --- |
| `artifacts/t213_budget_2000` | 2,000 | 2 | `token_budget` | 2,122 | 未覆盖 `detect_anomalies` | 25 |
| `artifacts/t213_nolimit` | 0 | 4 | `budget_exhausted`（步数预算） | 6,280 | 已覆盖 | 38 |
| `artifacts/t213_replay`（重放上面第 1 次） | — | 2 | `replayed` | —（不调模型） | 与源记录一致 | 25 |

读法：

- 2,000 的上限在第 2 次调用后触发（2,122 已超），没有第 3 次模型调用；
- 截断运行仍是 `status=succeeded`，但 `scope.met=false`、`warnings` 写明
  「token 预算已用尽…不能当作完整分析引用」——**成功 ≠ 完整**；
- 不设限的同一问题跑 4 步、6,280 token，说明 2,000 的预算确实会改变结果的完整度；
- 截断结果可离线重放，`replay.match=true`，结论数一致（25）。

### 22.6 取舍与限制

1. **usage 缺失时预算不生效**。这是本轮确认接受的取舍：宁可标注「未生效」，
   也不用估算值冒充账单。当前 DeepSeek 返回 usage，实测可用；换供应商需复核。
2. **只限 token，不限金额**。价格随供应商、缓存命中与折扣变化，离线无法核实。
3. **截断后仍可能「成功」**。判断完整性要看 `scope.met` 与 `warnings`，
   不能只看 `status`。
4. **重放不消耗 token**：重放结果的 `budget` 为空、`max_tokens=0`，这是那次运行的
   真实情况，不是丢失字段。
5. 预算按「调用后累计」判断，因此最后一次调用可能小幅超出上限（实测 2,122 / 2,000，
   超出 6.1%）。若要求严格不超，需要在调用前用上一次的平均值预估，会引入估算误差。

## 23. A 结论级评估（2026-10-23）

### 23.1 问题

T2.8/T2.9 的指标只回答「工具是否执行、跑了几步、结论有几条」，不回答「结论对不对」。

### 23.2 口径（先写后测）

| 对象 | 口径 |
| --- | --- |
| 异常点级 | 同系列、同一时间戳精确匹配；TP/FP/FN 逐点计 |
| 异常事件级 | 同系列、间隔 ≤ 3 小时合并为事件；检出事件与真值事件按时间区间重叠匹配 |
| 变化点 | 同系列、时间差 ≤ 2 个采样点；`weather_v1` 小时级即 ±2 小时 |

### 23.5 结论

1. **pipeline 的「检出 139 个异常点」不等于「139 个都对」。** 真值 18 个，
   点级 TP=18、FP=121，精确率 0.130；召回率 1.000。事件级同样只有 0.134 的精确率。
   这是本轮最重要的结果：以前的「异常检测 Precision 0.762」来自 `weather_eval_v1`
   的 dev/holdout 口径，不能直接搬到 `weather_v1` 的演示结论上。
2. **agent 的「少 9.08 条结论」主要是范围窄，不是算错。** 在 agent 实际执行
   `detect_anomalies` 的 7 个用例里，18/18 真值都命中，误报点与 pipeline 相同（121）。
   未执行的 6 个用例不是「检不出」，而是「根本没看」；按实例计少看 108 个真值实例。
   去重后 agent 漏 0 个真值异常事件。
3. **趋势结论有 1/2 站是错的。** `temperature@STA_A` 判为上升（正确），
   `temperature@STA_B` 判为下降（真值为上升）。原因不是公式算错，而是 Mann-Kendall
   在强季节周期 + AR(1) 噪声下被污染；结论自身已写「未做季节调整时强季节周期会污染
   趋势检验」，但这不改变「方向与注入真值相反」的事实。季节性 2/2 站通过容差。
4. **结论需求覆盖 14/14（有映射的期望项），但仍有 6 个期望项没有专门结论类别**
   （extreme / stationarity / autocorr / normality）。它们被标 `unlabeled`，不能把
   `need_coverage=1.00` 说成「所有问题都有结论」。
5. **数据质量只做到「报告了」而不是「定位到」。** 单位变化能定位到 STA_A 起点；
   缺失段、采样缺口、乱序块只有聚合告警/区间，没有逐站点起点，因此只记
   `reported_unlocalized`，不计算 P/R。

### 23.6 限制

- 13 个用例共用同一份 `weather_v1.csv`，跨用例累加是重复测量，不是 13 倍独立证据；

- 真值只覆盖注入的 18 个异常点和 2 个压力水平跳变；没有覆盖所有可能的真实异常。
- 趋势真值只有温度两站；湿度/气压/风速/降雨未注入趋势真值，标 `unlabeled`。
- 季节性容差（±3.0、±1 月）是本轮先写后测的选择，换数据须重新标定。
- 未改任何检测阈值；精确率低是检测器在演示集上的真实表现，不是本轮调参造成的。

### 24.4 结论

- 9.08 条/用例的差异 **100% 来自「没执行工具」**，不是「执行了但算少了」，也不是
  参数不同。拆开是：周期 90 条（6.92/用例）、异常检测 18 条（1.38/用例）、
  变化点 10 条（0.77/用例）。
- 这与 A 的结果互相印证：agent 在真正执行检测时，真值命中与 pipeline 相同；
  差异是分析范围，而不是检测精度。
- 因此不能再用「agent 结论少 23.3%」暗示「agent 质量差」；准确说法是
  「agent 按需少跑了周期/异常/变化点，精度未变，但报告广度下降」。
- 反过来，pipeline 的 507 条结论也不是「更多正确」：其中 130 条周期、130 条趋势、
  130 条季节性来自同一份数据的不同列/站点，重复度高；A 已证明异常结论精确率仅 0.13。

### 24.5 限制

- 归因只覆盖「结论条数」；同一条结论的文字是否更准确，B 不回答（A 只覆盖趋势/季节/异常/变化点）。

  `metrics` / `spectrum` 条数逐案看。

- 短数据上 `seasonal` 结论缺失，结论需求覆盖 0.7857；这不是 agent 选错工具，

### 26.3 运行设计（与任务卡的差异）

任务卡写「guided/free 各 5 次 × 6 用例」= 60 次，同时又写「总运行 ≤ 30 次」，
两者不能同时满足。本轮优先满足验收真正要的 **free 步数分布**：

```text
free    6 用例 × 5 次 = 30 次
guided  6 用例 × 1 次 = 6 次（只做完整性/范围下限检查，不当作分布）
合计 36 次，比 30 次多 6 次
```

这是有意偏离，不是漏跑。若坚持 ≤30 次，就只能把 free 降到 4 次/用例，分布样本
更薄；若坚持 guided 也 5 次，则 60 次、成本翻倍。选择理由与代价写在这里，后续可重跑。

运行参数：`deepseek-chat`、`rule` 计划、`guided`/`free` 对照、`--agent-max-tokens 6000`、
不重放（D 不验证重放）。

### 26.5 结论

1. **本批 free 没有低频抖动。** 30 次全部 5 步、39 条结论；每个用例的步数极差为 0。
   这比 T2.11 的 4 用例 × 3 次强，但仍不能说「free 永久稳定」——跨批次历史里仍有
   3 步 vs 5 步的记录，模型版本/提示变化都可能改变范围。
2. **free 在开放问题上稳定地跑满 5 个工具。** 6 个探针（开放/风险/对比）全部
   5 步；这说明当前模型在 free 下倾向于「全查」，而不是按问题压窄。
3. **guided 在开放问题上显著压窄。** 6 个探针只跑 2–3 步、25–29 条结论，

   已经被完整回答**；不能把 guided 的 2 步说成「开放问题只需 2 步」。
4. **6,000 token 对 free 偏低。** free 单次平均 7,030 token；`p_compare_station`
   有 3/5 次以 `token_budget` 结束。虽然这 3 次仍完成了 5 个工具与 39 条结论
   （预算检查发生在下次模型调用前，最后一次工具已执行），但 6,000 不是 free 的
   舒适上限。guided 平均 3,475 token，6,000 足够。
5. **成本差约 10 倍。** free 30 次 210,905 token，guided 6 次 20,849 token；
   按单次算 free 约 2 倍，按总样本算约 10 倍。开放问题若只需要「值得注意的点」，
   guided 更经济；若要求「尽量全查」，free 更完整但成本高。

### 27.2 发现：复算指标塌陷为 0

在配置了 `MTSA_LLM_*` 的机器上重跑 `evals.run_evals`，得到：

| 指标 | 已提交基线（HEAD） | 重跑（MTSA_PLANNER=auto） |

根因不是检测器退化，而是**计划层漂移**：

```text
MTSA_PLANNER=auto + 已配置模型
  → 天气评估的运行计划由 LLM 生成（plan_source=llm/cache）
  → 问题「分析温度的趋势、季节性与极端事件」只选了
     ['trend', 'seasonal', 'extreme']
  → engine 以 "anomaly" in plan.analyses 为门槛，异常检测根本没有执行
  → holdout 的 anomalies 为空，按 0 个检出计分
```

证据：`artifacts/eval_split/fold*/holdout_run/result.json` 中
`plan_source=llm`、`analyses=['trend','seasonal','extreme']`、`anomalies=[]`；
把同一折的问题改成含「异常」后，`analyses` 出现 `anomaly`，检出 21 个点。

这是评估链路的错误，不是模型或算法的失败。按纪律，先记录再修，不放宽任何阈值。

## 28. 方案 1：鲁棒性矩阵（2026-10-23）

### 28.1 目标与范围

Agent 边界 3。全部固定 `MTSA_PLANNER=rule`；Agent 用例只测前置边界，不调用真实模型。

契约先写后测：

1. 每个用例都必须返回 `AnalysisResult`，且失败也写 `result.json`；
2. 失败必须是可解释的 `error.code`，成功必须有 `report.md` 与结论；
3. 降级成功必须有 warning 或 quality issue，结论必须绑定证据；
4. 不允许把「检测器没执行」写成 0 分；
5. 小样本用例单例 < 30 s。

### 28.2 实测结果

### 29.3 口径修正：什么是「一个异常事件」

`evals/conclusion_eval.py::summarize()` 原先的 `event` 指标，是把**每个真值异常点**当成一个事件
（`start = end = 该点时间`）。v2 有 100 个异常点、但只有 30 个事件，于是 8 小时持续段会被算成
8 个独立事件，事件级指标实际退化成点级指标。

本章在 `evals/conclusion_gate_eval.py` 新增 `_event_metrics()`：

1. 真值侧：按标签 `event_id` 分组，`start = min(timestamp)`、`end = max(timestamp)`；
2. 检出侧：同一系列内间隔 ≤ 3 小时的点合并为一个事件；
3. 匹配：同系列、事件区间有交集才算命中，每个检出最多匹配一个真值；
4. 未执行：`detect_anomalies` 未运行的用例，把该用例全部真值事件计入召回分母（FN）。

`conclusion_eval.py` 的旧口径保持不变，避免改变历史报告；新口径只在方案 2 门禁中使用，
并在结果的 `anomaly.event` 中给出逐用例明细。

下一轮只要多 1 个误报或多漏 1 个真值就会失败。

**agent 与 pipeline 完全相同**，原因不是 agent 更强，而是：

- `guided` 下限把 compute_metrics / detect_anomalies / detect_change_points 固定为必做；
- 模型额外用 1 步执行 analyze_spectrum，随后想执行 run_stat_tests 时被
  `scope_exceeded` 拒绝（追加步数 1/1 已用尽），以 `budget_exhausted` 结束；
- 4 次中 3 次缺 `run_stat_tests`，但该工具不产出四类被评分的结论，所以结论级指标不变。

`budget_exhausted` 是 **guided 追加步数**预算，不是 token 预算：三次运行的 token 分别为
6,034 / 6,062 / 6,039（上限 8,000，`budget.exhausted=false`）。完整运行（v2_full_2）为 7,727 token。

### 29.6 失败溯源（为什么不是满分）

**漏掉的 1 个异常事件**：`temperature@STA_B`，2024-09-02 22:00 → 09-03 05:00（8 小时）。

- 注入幅度按残差尺度约 15–18σ，但检测器的 24 小时中心滚动中位数把这段抬升部分吸收：
  趋势项从 18.53 抬到 22.37，导致残差只有 +3.1～+4.9（z 4.12～6.60），低于阈值 8.0；
- 这不是 v2 的数据错误，而是「持续段长度接近季节窗口 1/3」时的已知检测边界；
- 同一段的前后小时出现 z≈−4～−5 的负残差，说明抬升被摊到了相邻点。

点级另漏 16 个/次：上述 8 点 + `humidity@STA_B` 持续段漏 7 点（07:00 命中，事件仍算命中）
+ `temperature@STA_A` 持续段尾部 1 点（08:00–15:00 中 09:00 漏检，事件仍命中）。

**变化点 4 个误报/次**（真实 2 个，检出 6 个）：

| 检出 | 统计量 | 性质 |
| --- | --- | --- |
| pressure@STA_A 2024-02-03 09:00 | 8.2447 | 真实 +60 hPa 跳变被递归二分切成两段，多出的前边界 |
| pressure@STA_A 2024-06-12 03:00 | 0.9309 | 年周期造成的弱分割（medium） |
| rainfall@STA_A 2024-06-26 23:00 | 7.4443（variance） | 单点极端降雨被误判为方差突变 |
| rainfall@STA_B 2024-10-15 16:00 | 5.4357（variance） | 同上 |

两个真实变化点（`pressure@STA_A` 2024-02-29 23:00、`pressure@STA_B` 2024-07-19 00:00）
都被命中，召回 1.0；F1 低完全来自精度（0.3333）。这暴露的是变化点检测器缺少
「最小效应量/显著性门槛」和「单点极端值鲁棒化」，不是阈值标定问题。按本章边界，
不为此修改检测器；如需改进，应另立任务并重跑全部评估。
